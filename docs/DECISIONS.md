# 설계 결정 기록

각 항목은 **문제 → 결정 → 근거 → 되돌릴 때 주의점** 순서입니다.
코드를 되돌리기 전에 해당 항목을 먼저 읽으세요.

---

## 1. 카드군 동일성은 등록 시점에 결정론적 게이트로 판정한다

**문제.** LLM이 같은 컨셉을 매번 다른 표기로 뱉어 `홍련의 검사단`, `홍련 검사단`,
`홍련검사단`이 전부 별개 카드군으로 누적됐습니다.

원인은 두 가지가 겹쳐 있었습니다.

1. `registerNewArchetype()`의 중복 검사가 **완전 일치(`===`)뿐**이라 공백·조사 하나
   차이로 신규 생성됐습니다.
2. 유사도 매칭 함수 `findMatchingArchetype()`이 이미 있었지만 `if (data.themeName)`의
   `else` 가지에만 걸려 있었고, 프롬프트 스키마가 `themeName`을 필수로 요구해서
   **한 번도 실행되지 않는 죽은 코드**였습니다.

**결정.** `resolveArchetype()` 게이트를 `registerNewArchetype()` 앞단에 두고, 다음 순서로
판정합니다. 전부 동기 처리이며 임베딩이나 추가 LLM 호출을 쓰지 않습니다.

```
1. id 완전일치
2. 과거 흡수된 별칭(aliases) 일치
3. 키워드 완전일치 (2글자 이상)
4. 정규화 이름 완전일치      ← 공백/조사 '의'/구두점 제거 후 비교
5. 키워드가 상대 이름에 포함
6. 이름 포함관계 (3글자 이상)
7. bigram Dice 계수 ≥ 0.82
8. 0.70~0.82 회색지대 + comboAction 일치
9. 공통 어미 명사 + comboAction + element 모두 일치
```

**근거.** LLM에게 "중복 만들지 마"라고 지시하는 것만으로는 안 됩니다. 이건 생성 문제가
아니라 엔티티 해소(entity resolution) 문제라서, 생성 결과를 결정론적 로직으로 감싸야 합니다.
프롬프트 지시는 1차 방어일 뿐이고 게이트가 최종 방어선입니다.

임베딩을 쓰지 않은 이유: 로컬 Ollama에 임베딩 모델이 깔려 있다는 보장이 없고, 한국어
카드군명은 정규화 + 문자열 유사도만으로 충분히 잡힙니다. 비용도 0입니다.

`comboAction`을 회색지대 판정에 쓴 이유: 값이 8종뿐이라 blocking key로 신뢰도가 높습니다.

**임계값.** `ARCHETYPE_SIM_STRONG = 0.82`, `ARCHETYPE_SIM_WEAK = 0.70`
(`archetype-service.js`). 과하게 합쳐지면 올리고, 중복이 새면 내리세요.

**되돌릴 때.** 게이트를 빼면 표기 변형이 다시 무한 증식합니다. 임계값 조정으로
해결되는지 먼저 확인하세요.

**검증 기록.** 병합 5/5, 오탐 0/4. 특히 `화염 기사단` vs `서리 기사단`은 어미가 같아도
속성·연계가 달라 정상적으로 분리 유지됩니다.

## 2. 카드 이름에 카드군 키워드를 강제 포함시킨다

**문제.** 덱 서치 콤보가 `card.name.includes(theme.keyword)`로 소속을 판정하는데,
프롬프트가 카드 이름에 키워드를 넣으라고 지시하지 않았습니다. 이름에 키워드가 없는 카드는
같은 카드군인데도 **서치 대상에서 누락**됐습니다.

**결정.** 유희왕 실제 룰을 따릅니다. 프롬프트에서 1차로 지시하고, 그래도 빠지면
`enforceKeywordInName()`이 이름 앞에 키워드를 붙여 보정합니다.

**근거.** 소속 판정이 문자열 포함 검사로 확정되어 애매함이 사라집니다.

**되돌릴 때.** 키워드 강제를 빼려면 콤보의 소속 판정을 `themeId` 기준으로만 하도록
`archetype-combos.js`의 `belongsToTheme()`도 함께 고쳐야 합니다. 한쪽만 바꾸면
서치가 조용히 실패합니다.

## 3. 콤보는 데이터 테이블, 상태이상은 단일 소스

**문제.** `triggerArchetypeCombo`(플레이어용)와 `triggerBossArchetypeCombo`(보스용)가
각각 8개 if 분기를 통째로 들고 있어 약 280줄이 중복이었습니다. 액션 하나를 추가하려면
두 함수를 모두 고쳐야 했고, `action === 'search' || action === 'hero_search'` 같은
별칭 검사가 16번 반복됐습니다.

**결정.** `archetype-combos.js`에 `ARCHETYPE_COMBO_ACTIONS` 테이블을 두고
`{ label, player(ctx), boss(ctx) }` 형태로 정의합니다. `runArchetypeCombo(side, ...)`가
디스패치합니다. 상태이상도 같은 방식으로 `status-effects.js`에 모았습니다.

**근거.** 액션 추가 비용이 "두 함수 수정"에서 "엔트리 한 개 추가"로 줄어듭니다.
별칭 정규화도 `normalizeComboAction()` 한 곳에서만 일어납니다.

## 4. ⚠️ 카드군 스탯 시너지는 쓰지 않는다 (되살리지 말 것)

**경위.** 코드에 `bonusAtk`을 **읽는** 코드는 두 곳 있는데 **만드는** 코드가 없어
값이 항상 `undefined → 0`이었습니다. 리팩터링 중 이를 버그로 판단해
"같은 카드군 2체 +2 / 3체 +4 / 4체 +6"을 구현했습니다.

**정정.** 이 게임은 오토체스가 아니라 **유희왕식 연계**를 지향합니다. 종족 스탯 시너지는
원래 제거하려던 방향이었고, 위 구현은 의도에 반하는 것이었으므로 **전량 되돌렸습니다.**

**현재 상태.** `evaluateFieldSynergy()`는 `bonusAtk`을 만들지 않습니다. 전개 수(`count`)는
UI 배너 표시용이며, 필드 카드에는 테두리(`ring-1`)만 표시됩니다. 공격력 계산은
`entity.attack` 그대로입니다.

**전개 수가 의미를 갖는 유일한 정상 경로**는 `chainDamage` 콤보입니다 — 같은 카드군 아군이
필드에 있으면 연계 피해가 8 → 12로 올라갑니다. 스탯이 아니라 **연계 위력**입니다.

**되돌릴 때.** 되돌리지 마세요. 스탯 보너스가 필요해 보이면 그건 대개 "연계가 약하다"는
신호이므로, 새 콤보 액션을 추가하는 쪽으로 해결하세요.

**검증 기록.** 공격력 10 유닛이 같은 카드군 1/2/3/4체 전개 상태에서 전부 정확히 10 피해.

## 5. 상태이상은 등록 → 매 턴 틱 → 감쇠

**문제.** `bossStatus.burn / poison / shock`은 **쓰기만 하고 읽는 코드가 없어** 완전히
무효과였습니다. 카드에 "🔥 화상 6" 뱃지가 표시되는데 실제로는 아무 일도 없었습니다.
`vulnerable`은 읽히긴 했지만 **차감 로직이 없어 한 번 걸리면 전투 끝까지 지속**됐습니다.
보스 카드의 화상/맹독은 그 자리에서 HP를 한 번 깎고 사라져 "3턴 지속"이라는 설명과
동작이 달랐습니다.

**결정.** `status-effects.js`가 `{ [type]: { turns, value } }` 형태로 관리하고,
정의(`STATUS_EFFECTS`)에 선언된 플래그(`dot`, `blocksTurn`, `damageTakenMultiplier`,
`bonusOnHit`)에 따라 자동 동작합니다. 중첩은 "더 강한 쪽"만 남겨 폭주를 막습니다.

**적용 지점.**
- 보스 지속 피해 → `executeBossTurn()` 시작
- 플레이어 지속 피해 → `startPlayerTurn()`
- 감쇠 → 각 진영 턴 종료

**검증 기록.** 맹독 3턴 부여 시 보스 HP 130 → 122 → 114 → 106 (총 24) 후 정확히 만료.

## 6. LLM 출력은 신뢰하지 않는다 — 3단계 JSON 복구 + 스탯 클램핑

**문제.** 로컬 4B급 모델은 JSON을 자주 깨뜨리고, 스탯 인플레이션을 일으킵니다.

**결정.**
- `repairAndParseJson()` — 정상 파싱 → 문법 보정 → 정규식 필드 추출 3단계
- `sanitizeAndClampCardData()` — 등급별 상한으로 강제 클램핑, `%` 표기를 정수로 치환

**근거.** 카드 생성이 실패하면 사용자 경험이 크게 나빠집니다. 모델을 바꿔도 이 방어층은
유지해야 합니다 — 모델마다 깨지는 양상만 달라질 뿐 깨지는 건 똑같습니다.

## 7. 프롬프트에 싣는 카드군 목록은 상위 40개로 제한한다

**문제.** 카드군이 무한 누적되면 `getArchetypesPromptSummary()`가 만드는 문자열이
로컬 LLM의 컨텍스트를 잡아먹습니다.

**결정.** 보유 카드 수 기준 상위 40개만 싣고, 나머지는 `(그 외 N개 카드군 생략)`으로 표시합니다.

**부작용.** 생략된 카드군은 LLM이 재사용할 수 없어 유사 카드군이 새로 생길 수 있습니다.
다만 등록 게이트(#1)가 흡수하므로 실제 중복으로 이어지지는 않습니다.

## 9. 이스케이프 유틸을 도입한다

**문제.** `onclick="showKeywordInfo('${card.themeName}')"`처럼 LLM 생성 문자열을 그대로
인라인 핸들러에 박아서, 이름에 작은따옴표 하나만 있어도 속성이 깨지고 클릭 핸들러가
통째로 죽었습니다.

**결정.** `dom-utils.js`에 `escapeHtml()` / `escapeJsString()`을 두고 카드·카드군 이름이
들어가는 모든 지점에 적용했습니다.

**검증 기록.** `홍련's "검사단" <b>테스트</b>`를 카드명으로 넣어도 문자 그대로 렌더되고
onclick 핸들러가 전부 문법적으로 유효합니다.

## 10. `initBattle()`은 `isAnimating`을 리셋한다

**문제.** 보스 턴 도중(`isAnimating === true`)에 전투를 리셋하면 플래그가 true로 남아
`playCard` / `attackWithMinion` / `playerEndTurn`이 전부 조기 반환해 **조작이 영구 잠겼습니다.**

## 11. 시각 프롬프트는 LLM(의미) + 코드(형식)로 나눈다

**문제.** LLM에게 완성된 28개 Danbooru 태그를 요구하고 있었습니다. 소형 모델은
Danbooru 문법에 약하고, 출력이 길수록 JSON이 깨집니다.

**첫 시도(실패).** LLM에서 태그 생성을 완전히 걷어내고 **코드가 한국어를 직접
영어 태그로 번역**하게 만들었습니다. 곧바로 오탐이 터졌습니다 — 카드 효과 설명에
항상 들어가는 **"피해"**에서 `피`가 `blood`로, `해`가 `water splashes`로 잡혀
화염 카드에 물 태그가 붙었습니다. 한 글자 한국어 키는 흔한 단어에 파묻힙니다.

**결정.** 역할을 이렇게 나눕니다.

- **LLM** → `visualSeeds`: 영어 핵심 키워드 3~6개 (`crimson swordsman, flaming katana`)
- **코드** → `expandDanbooruTags()`가 태그 문법·동시등장·개수로 확장

**근거.** NovelAI는 영어를 먹고 LLM은 이미 좋은 번역기입니다. 의미 파악은 LLM이,
기계적인 태그 확장은 코드가 맡는 것이 양쪽 모두에게 쉬운 일입니다. 키워드 몇 개는
전체 태그 목록보다 훨씬 짧아서 JSON 안정성도 확보됩니다.

**한국어 사전의 현재 위치.** `KOREAN_CONCEPT_SEEDS`(44항목)는 **폴백 전용**입니다 —
LLM 실패/오프라인, 그리고 `visualSeeds`가 없는 구버전 카드의 이미지 리롤.
사전을 손볼 때는 `dan-tag-gen.js`의 **"한 글자 키 금지"** 규칙 주석을 먼저 읽으세요.

**되돌릴 때.** 코드만으로 한국어를 번역하려는 시도는 이미 실패했습니다. 반복하지 마세요.

## 12. 모델 계열별 설정을 프로파일 테이블로 분리한다

**문제.** `stop: ['<|im_end|>', '<|endoftext|>']`(ChatML/Qwen 전용)과
`think: false`(Qwen 3 전용)가 하드코딩돼 있었습니다. 다른 모델로 바꾸면 종료 토큰이
안 걸려 모델이 JSON 뒤에 잡설을 붙입니다.

**결정.** `ai-service.js`에 `MODEL_PROFILES` 테이블을 두고 이름 정규식으로
`stop` / `thinking`을 분기합니다. 계열을 못 찾으면 `stop`을 비워
Ollama가 모델 템플릿 기본값을 쓰게 합니다(잘못된 토큰보다 안전).

**근거.** 모델 교체 비용을 "여러 곳 수정"에서 "테이블 한 줄 추가"로 낮춥니다.

## 13. Gemma 4 E4B 대신 Qwen 3.5 4B를 유지한다

**검토 결과.** Gemma 4 E4B(2026-04-02 출시)는 실존하며 두 모델 다 유효한 선택지이지만,
벤치마크가 Qwen 우세를 명확히 보여줍니다.

- MMLU-Pro 69.4 vs **79.1**, GPQA 58.6 vs **76.2**
- **TAU2(구조화/도구 사용) 42.2 vs 79.9** ← 이 프로젝트의 JSON 출력과 가장 가까운 지표
- Gemma 우위는 MMMLU **+0.5**뿐 (오차 범위)
- 메모리: Gemma 약 5GB vs Qwen 약 4GB (Gemma는 총 8B 파라미터)
- Qwen 3.5는 201개 언어 중 **한국어 depth를 명시**

**결정.** Qwen 3.5 4B 유지. 다만 #12로 코드는 모델 중립화해 두었으므로
나중에 교체하려면 프로파일 한 줄만 추가하면 됩니다.

**참고.** 한국어 품질 문제의 실제 원인은 모델이 아니라 샘플링 파라미터
(presence/frequency penalty 중복)일 가능성이 높다고 판단해 그쪽을 먼저 고쳤습니다.

## 14. ⚖️ 카드 성능은 수치가 아니라 '효과 예산'으로 평가한다

**문제.** `sanitizeAndClampCardData()`가 공격력·체력 같은 **숫자만** 클램핑하고
효과의 개수·강도는 보지 않았습니다. 그래서 이런 카드가 통과했습니다.

- RARE [심연의 암살자] — 실드관통 + 흡혈 + 처형 (프리미엄 키워드 3종)
- RARE [성역의 수호사제] — 방어막 + 치유 + **무적**
- COMMON 카드가 "모든 피해 무효화 + 드로우 2 + 광역"

**결정.** `config.js`에 효과별 **파워 점수**와 **최소 요구 등급**을 정의하고
(`EFFECT_COSTS`), 등급별 예산(`RARITY_EFFECT_BUDGET`)을 넘거나 등급 요건에
미달하는 효과를 잘라냅니다.

| 등급 | 예산 | 새로 열리는 효과 |
|---|---:|---|
| common | 2 | 피해·방어막·치유·상태이상 |
| rare | 4 | 드로우·마나수급·연타·치명타·흡혈·광역·실드관통 |
| epic | 7 | 처형·더블캐스트 |
| legendary | 10 | 무적 |

추가로 효과가 예산의 70%를 넘게 쓰면 스탯을 해당 등급 범위의 하위권으로 끌어내려
**수치와 효과를 함께** 평가합니다.

**되돌릴 때.** 수치만 보는 밸런싱으로는 "COMMON인데 무적" 같은 카드를 막을 수 없습니다.
새 효과 키워드를 추가하면 **반드시 `EFFECT_COSTS`에도 등록**하세요. 등록되지 않은
효과는 예산 계산에서 누락되어 밸런스 구멍이 됩니다.

**검증 기록.** RARE [암살자] 11점 → 4점(관통 유지, 흡혈·처형 제거),
RARE [수호사제] 7점 → 2점(무적만 제거), LEGENDARY [검성] 7/10점 무변경.

## 15. 🐛 `sanitizeAndClampCardData`는 `skills[]`도 읽어야 한다

## 17. 카드 이름에 키워드를 강제하지 않는다 (#2 번복)

**정정.** 유희왕이 그 룰을 쓰는 이유는 **물리 카드라 DB 조회가 불가능해서**입니다.

**결정.**
- 소속 판정의 **단일 권위는 `themeId`**. `belongsToTheme()`의 이름 매칭은

- 프롬프트는 "자연스럽게 녹이면 좋다"고 **권장만** 합니다.

**되돌릴 때.** 이름 강제를 되살리려면 `cleanCardName`이 아니라 새 함수를 만드세요.
과거 구현은 조사 중복(`빙결의 동결의`)과 마커 찌꺼기(`빙결의 절 서리의`) 문제가 있었습니다.

## 18. 카드군 중복은 게이트 + LLM 피드백 2단으로 막는다

**문제.** 결정론적 게이트(#1)는 **표기 변형**은 잘 잡지만 **의미는 모릅니다.**
`빙결의 절도`(키워드 절)와 `영토 동결령`(키워드 동결)은 둘 다 물 속성 결빙
카드군인데 문자열 유사도가 0에 가까워 별개로 남았습니다.

**결정.** `archetype-proposal.js`에 2단 판정을 둡니다.

1. 게이트 점수가 `ARCHETYPE_SIM_STRONG`(0.82) 이상 → **조용히 흡수** (LLM 호출 없음)
2. 회색지대 → `findRivalArchetypes()`가 **속성·연계 일치까지 포함해** 후보를 찾고,
   후보가 있으면 LLM에게 "같은 카드군인가?"를 되묻습니다
   (`askLLMToDisambiguate`, temperature 0.3)
3. LLM이 `merge`면 기존 id 채택, `distinct`면 더 구별되는 이름·키워드로 재명명 후
   게이트 재검사

**비용.** 회색지대일 때만 LLM을 1회 더 호출합니다.
카드팩(5장)은 `allowFeedback: false`로 게이트만 씁니다.

**검증 기록.** `빙결의 절도`(water/freeze) 후보 탐색이 `서리 마법결사`를
risk 0.50(속성 일치 + 연계 일치)으로 정확히 탐지.

## 20. 카드군 목록을 프롬프트에 통째로 싣지 않는다 (컨텍스트 초과)

**문제.** `getArchetypesPromptSummary()`가 카드군 전체(상한 40개)를 매 카드 생성
프롬프트에 주입했습니다. 실측하니:

| 카드군 수 | 주입 크기 | num_ctx 8192 대비 |
|---:|---:|---:|
| 8개 (현재) | 약 1,970토큰 | 24% |
| 40개 (상한) | 약 7,560~8,640토큰 | **92~105%** |

상한에 도달하면 **카드군 목록만으로 컨텍스트가 넘쳐** 카드 설계 지시와 출력 스키마가

**결정.** 두 가지를 동시에 적용했습니다.

1. **설명문을 60자로 컷** + 기본 표시 개수를 40 → 12로 축소 (폴백 경로)
2. **의미 검색으로 top-6만 주입** (`getRelevantArchetypesPrompt`) — 임베딩 모델이 있을 때

**검증 기록.** 카드군 40개 기준

**되돌릴 때.** 전체 목록을 싣는 방식으로 돌아가면 카드군이 늘어나는 순간 생성 품질이
무너집니다. 표시 개수를 늘리고 싶으면 설명문 컷 길이부터 줄이세요.

## 21. 한국어 임베딩으로 의미 기반 카드군 판정을 한다

**문제.** 문자열 유사도는 **표기 변형**만 잡습니다. 의미는 모릅니다.
`빙결의 절도`(키워드 빙결)와 `영토 동결령`(키워드 동결)은 bigram Dice 계수가
0에 가깝지만 둘 다 물 속성 결빙 카드군입니다.

한국어 동의어(빙결/동결/결빙/서리/한파)를 손으로 사전에 넣는 방법은 이미
`dan-tag-gen.js`에서 실패했습니다(결정 #11). 반복할 이유가 없습니다.

**결정.** `embedding-service.js`를 신설하고 Ollama의 임베딩 API를 씁니다.

- 기본 모델 **`bge-m3`** (BAAI, 1024차원, 8K 컨텍스트, 100개 언어, 약 1.2GB)
  Ollama 공식 라이브러리에 있고 한국어 성능이 검증돼 있습니다.
- 벡터는 `archetypesList`가 아니라 **별도 IndexedDB 키**에 저장합니다.
  1024차원 × N개를 카드군 레코드에 넣으면 localStorage 백업이 터집니다.

**판정 임계값 — 실측 보정 (bge-m3)**

처음 잡은 0.88/0.75는 감이었고 **전부 틀렸습니다.** 실측 후 교정했습니다.

| 코사인 유사도 (**같은 속성 안에서만**) | 처리 |
|---|---|
| ≥ 0.72 | 같은 카드군으로 병합 |
| 0.60 ~ 0.72 | 회색지대 → LLM에게 되묻는다 (#18) |
| < 0.60 | 별개 |

**⚠️ 속성 하드 게이트가 없으면 임계값으로 분리가 불가능합니다.**

| 쌍 | 유사도 | |
|---|---:|---|
| 화염 기사단 / 서리 기사단 | 0.731 | 별개여야 하는데 높게 잡힘 |
| 빙결의 절도 / 영토 동결령 | 0.669 | 병합해야 하는데 위보다 **낮음** |

bge-m3는 기대했던 심층 의미보다 **표층 구조**에 강하게 반응합니다.
"X 기사단"처럼 구조가 같으면 의미가 달라도 가깝게 잡히고, 구조가 다르면
의미가 같아도 멀게 잡힙니다. 임베딩 입력에서 속성·연계를 빼봐도 오히려
나빠졌습니다(마진 −0.062 → −0.166).

그래서 `compareArchetypeSemantics()`는 **속성이 다르면 유사도를 계산조차 하지 않고**
`distinct`를 돌려줍니다. `findSimilarArchetypes()`의 `element` 옵션도 정체성
판정에서는 필수입니다(프롬프트용 검색에는 넘기지 마세요).

속성으로 자른 뒤의 분리 마진은 **+0.088** (병합 최솟값 0.669 − 별개 최댓값 0.581).

**검증 기록.** 9/9 통과. `빙결의 절도 / 영토 동결령`(0.669)은 회색지대로 분류되어
LLM이 최종 판단합니다 — 자동 오판보다 안전합니다.

**성능.** 최초 벡터 생성(40개) 약 3.2초는 앱 시작 시 1회뿐이고 IndexedDB에 저장됩니다.
이후 의미 검색은 평균 **76ms**로, LLM 생성(3~6초) 대비 무시할 수준입니다.

**⚠️ 임베딩 모델은 선택입니다.** 없으면 `checkEmbeddingAvailable()`이 false를 돌려주고
모든 함수가 null/빈 배열을 반환해 **문자열 판정으로 자동 폴백**합니다.
게임은 정상 동작하며 콘솔에 설치 안내만 한 번 뜹니다.

```bash
ollama pull bge-m3
```

**되돌릴 때.** 임베딩을 빼면 의미가 같고 표기가 다른 카드군이 다시 난립합니다.
문자열 임계값을 낮춰 대응하려 하면 오탐(서로 다른 카드군이 합쳐짐)이 늘어납니다.

## 22. 카드군 결정을 위해 LLM을 2번 호출하지 않는다

**검토.** "호출 #1에서 카드군을 정하고 호출 #2에서 카드를 생성"하는 2단 구조를
검토했습니다.

**결정.** 채택하지 않았습니다. **임베딩이 대부분의 판정을 무료로 해결**하기 때문입니다.

- 유사도 ≥ 0.88 → 결정론적 병합. LLM 호출 0회
- 유사도 < 0.75 → 신규. LLM 호출 0회
- 회색지대만 LLM 1회 추가 (#18의 피드백 루프)

2단 구조는 **모든 카드**에 생성 1회를 추가하는데, 로컬 모델은 프롬프트 처리보다
생성이 훨씬 느립니다. 회색지대에만 지불하는 편이 낫습니다.

카드팩(5장)은 비용 때문에 `allowFeedback: false`로 임베딩 게이트만 씁니다.

## 23. 카드군이 카드 속성을 제약한다 (속성 정책)

**문제.** 카드군과 카드 속성이 따로 놀았습니다. "홍련(화염) 카드군"에 물 속성 카드가
들어가도 아무도 막지 않았습니다.

**결정.** `archetype-identity.js`에 속성 정책을 둡니다.

| 정책 | 최대 속성 | 상극 허용 | 설명 |
|---|---:|---|---|
| `mono` | 1 | ✗ | 단일 속성. 정체성이 가장 뚜렷 |
| `dual` | 2 | ✗ | 두 속성. **상극 조합 금지** |
| `multi` | 6 | ✓ | 다속성. 속성 전환 자체가 컨셉 (엘리멘틀 히어로형) |

**상극 쌍:** 화염↔물 · 번개↔자연 · 신성↔암흑

- `sanitizeElementPolicy()` — 등록 시 상극 조합을 제거하고 개수 상한을 적용
- `coerceCardElement()` — 카드 속성이 카드군 정책 밖이면 대표 속성으로 교정

**검증 기록.** `dual [fire, water]` → `[fire]`로 교정, `multi`는 상극 허용,
`[홍련의 검사단] + water` → `fire`로 교정.

## 24. 카드군 고유 연계 = 액션 × 발동조건 × 증가방식

**문제.** 연계가 공통 액션 8종뿐이라 카드군이 8가지 맛밖에 안 났습니다.
"이 카드군은 서치형"이라는 것 외에 할 말이 없었습니다.

**결정.** 액션에 두 축을 더합니다. **효과는 여전히 하나입니다**(#16 유지) —
달라지는 건 *언제* 터지고 *얼마나* 세지느냐입니다.

**발동조건 (`comboTrigger`)** — 조건이 안 맞으면 발동하지 않습니다.

| 값 | 의미 |
|---|---|
| `always` | 카드를 낼 때마다 |
| `archetypePair` | 같은 카드군이 필드에 2장 이상일 때 (전개형) |
| `lowHp` | 내 체력 절반 이하 (역전형) |
| `bossShielded` | 보스가 방어막 보유 시 (카운터형) |
| `handRich` | 손패 5장 이상 (자원형) |
| `lateGame` / `earlyGame` | 5턴 이후 / 3턴 이내 |

**증가방식 (`comboScaling`)**

| 값 | 의미 |
|---|---|
| `flat` | 고정 |
| `perAlly` | 같은 카드군을 많이 깔수록 |
| `perTurn` | 턴이 길어질수록 |
| `perHand` | 손패가 많을수록 |

조합하면 8 × 7 × 4 = **224가지 연계 성격**이 나오지만 엔진은 여전히 8개 구현만
들고 있습니다. 실행 가능성과 다양성을 동시에 얻는 구조입니다.

> 보스 쪽은 발동조건을 검사하지 않습니다. 보스는 턴마다 카드를 몰아 내므로
> 조건까지 걸면 체감이 너무 약해집니다.

**검증 기록.** 홍련(archetypePair × perAlly) 실전 테스트 —
1장째 "연계 대기(조건: 같은 카드군 2장 이상)" → 2장째 8 피해 → 3장째 10 피해.

## 25. 카드군 초기화는 카드를 보존한다

**문제.** 게이트·임베딩이 없던 시절에 쌓인 이상한 카드군을 청소하고 처음부터
다시 쌓고 싶은 요구가 있었습니다.

**결정.** `resetArchetypes()`가 LLM 생성 카드군을 제거하고 기본 카드군 8종만 남깁니다.

**⚠️ 카드는 기본적으로 삭제하지 않습니다.** NovelAI 이미지 생성 비용이 들어간
자산이기 때문입니다. 소속만 잃고 `isGeneric: true`인 범용 카드가 되며, 나중에
다시 카드군에 편입시킬 수 있습니다.

```js
await resetArchetypes({ dryRun: true });                    // 미리보기
await resetArchetypes();                                     // 카드 보존 (기본)
await resetArchetypes({ deleteCards: true });                // 카드까지 삭제
await resetArchetypes({ keepDefaults: false });              // 기본 카드군도 제거
await restoreArchetypeReset();                               // 되돌리기
```

임베딩 벡터도 함께 정리되고 기본 카드군 벡터가 다시 생성됩니다.

**검증 기록.** 카드군 11 → 8, 카드 15장 전량 보존, 고아 카드 0건, 복원 정상.

## 26. 기본 카드군은 data.js 정의를 저장본에 동기화한다

**문제.** `loadArchetypes()`는 **없는 카드군만 추가**하고 이미 저장된 것은 건드리지
않습니다. 그래서 `data.js`에서 기존 카드군의 속성 정책·설명을 고쳐도
**이미 플레이 중인 사용자에게는 영원히 반영되지 않았습니다.**

보옥수/히어로를 다속성으로 바꿨는데 저장본은 그대로 `(없음) [holy]`였습니다.

**결정.** `repairArchetypeRecords()`가 시작 시 기본 카드군의 **정의 필드**를
`data.js`와 동기화합니다.

동기화 대상: `name` `title` `keyword` `icon` `badge` `description`
`element` `elements` `elementPolicy` `comboAction` `comboTrigger` `comboScaling` `synergy`

보존 대상: `aliases`(흡수 이력) · `createdAt` · `seeds`(합집합으로 병합)

**되돌릴 때.** 이 동기화를 빼면 `data.js` 수정이 신규 사용자에게만 적용되어
"내 화면에선 되는데 저장본에선 안 된다"는 재현 불가 버그가 생깁니다.

## 27. 기본 카드군 8종의 속성 정책

| 카드군 | 정책 | 속성 |
|---|---|---|
| 홍련의 검사단 | mono | fire |
| 서리 마법결사 | mono | water |
| 뇌제 발키리아 | mono | lightning |
| 성역의 수호사제 | mono | holy |
| 심연의 그림자단 | mono | dark |
| 세계수의 수호자 | mono | nature |

## 28. 전투 무작위는 시드 PRNG를 거친다 (P2P 락스텝 전제)

**문제.** 전투 경로에 `Math.random()` 9곳 + `Date.now()` 1곳이 있었습니다.
덱 셔플, 손패 파기 대상, 소환수 선택 등입니다. P2P 대전에서는 양쪽 클라이언트가
**같은 시드로 같은 결과**를 내야 하는데(락스텝) `Math.random()`으로는 불가능합니다.

**결정.** `rng.js`에 mulberry32 기반 `SeededRng`를 두고 전투의 모든 무작위를
여기로 통과시킵니다. `initBattle({ seed })`로 시드를 주면 전투가 그대로 재현됩니다.

**부수 이득.** 셔플이 `sort(() => 0.5 - Math.random())`에서 Fisher-Yates로 바뀌었습니다.
기존 방식은 **분포가 균일하지 않고 엔진마다 결과가 다릅니다.**

**⚠️ 전투 로직에서 `Math.random()`을 직접 쓰면 그 지점에서 동기화가 깨집니다.**
반드시 `battleRng()`를 쓰세요. (카드 생성·이미지 등 전투 밖은 무관)

**검증 기록.** 같은 시드 2회 → 덱·손패·보스덱·부하 전개가 완전 일치.
다른 시드 → 다름. 셔플 균일성 6000회 테스트에서 각 위치 1466~1539 (기대 1500).

## 29. 전투 진영을 Side 추상화로 대칭화한다

**문제.** 배틀 엔진이 PvE 전용이라 플레이어와 보스가 서로 다른 필드에 살았습니다.

| | 플레이어 | 보스 |
|---|---|---|
| HP | `state.playerHp` | `state.currentBoss.currentHp` |
| 방어막 | `state.playerMaxShield` | `state.currentBoss.shield` |
| 마나 | `state.playerMana` | **없음** |
| 덱·손패 | `playerDeck` / `playerHand` | `bossDeck` / `bossHand` |

그래서 "피해를 준다", "카드를 낸다" 같은 동작이 진영마다 별개 코드였고,
PvP를 얹으려면 전부 다시 써야 했습니다.

**결정.** 저장 구조는 **그대로 두고** 게터/세터 접근자(`Side`)를 씌웁니다.

```js
sides.player.hp -= 7;   // → state.playerHp 가 실제로 변경됨
sides.boss.hp -= 5;     // → state.currentBoss.currentHp 가 변경됨
```

기존 세이브 파일과 UI 코드를 건드리지 않으면서 대칭 로직을 쓸 수 있습니다.
PvP를 붙일 때는 두 번째 플레이어 Side를 만들어 같은 함수에 넘기면 됩니다.

**진영 공용으로 옮긴 동작** (`combat-side.js`)
`canPlayCard` · `drawTo` · `discardRandom` · `growMana` · `refreshMinions` · `describeSide`

**⚠️ 새 전투 로직은 `state.playerHp`를 직접 만지지 말고 `side.hp`를 쓰세요.**
그래야 진영을 바꿔 끼울 수 있습니다.

**남은 비대칭.** 보스는 아직 마나가 없습니다(PvE 스크립트 AI). `side.mana`는
가상값 99를 돌려주어 대칭 코드가 깨지지 않게 합니다. PvP로 갈 때 이 부분을
진짜 마나로 바꾸고 보스의 `comboPatterns`(스크립트 다단계 턴)를 걷어내면 됩니다.

**검증 기록.** `side.hp ↔ state` 양방향 연결 확인, 시전 조건 검사 3케이스 통과,
실전 스모크 정상.

## 30. 멀티플레이 방향 (미착수 — 설계만)

**측정 결과.** 덱 전체를 넘기는 데 **5.2KB**면 됩니다.

| | 크기 |
|---|---:|
| 대전 필수 카드 데이터 (13장, 이미지 제외) | 4.4KB |
| 카드군 정의 (연계 실행용, 5개) | 0.8KB |

카드군 정의가 작은 이유는 연계가 **고정 어휘의 enum**이기 때문입니다.
상대는 아래 9개 필드만 받으면 자기 카드군 DB 없이도 연계를 똑같이 실행합니다.

```json
{ "id":"...", "keyword":"홍련", "comboAction":"chainDamage",
  "comboTrigger":"archetypePair", "comboScaling":"perAlly",
  "elementPolicy":"mono", "elements":["fire"] }
```

**이미지는 별도.** AI 생성 카드는 base64 WebP라 장당 50~140KB → 12장이면 0.7~1.7MB.
카드 데이터를 먼저 보내고 이미지는 나중에 받는 방식을 권합니다.

**치트 방지는 이미 있습니다.** 받은 덱을 `sanitizeAndClampCardData()`에 통과시키면
COMMON에 무적 박은 카드가 와도 효과 예산 시스템(#14)이 자동으로 잘라냅니다.

**연결 방식.** 최소 시그널링 서버(방 코드 입력) + WebRTC 데이터 채널로 결정.
실제 게임 데이터는 P2P 직통, 서버는 연결 주선만 담당합니다.

**착수 전 남은 일.** 보스 마나 시스템 도입, `comboPatterns` 제거 또는 AI 전용화,
턴 진행을 진영 루프로 일반화.

## 31. PvE와 PvP는 억지로 합치지 않고 모드로 가른다

**문제.** 완전 대칭 엔진으로 통일하려면 보스에게 마나를 줘야 하는데,
그러면 PvE 밸런스가 통째로 흔들립니다.

**결정.** 공용 로직(피해·상태이상·연계·타겟팅)은 공유하고 **다른 부분만 모드로** 가릅니다.

| | PvE | PvP |
|---|---|---|
| 상대 마나 | 없음 (가상 99) | 플레이어와 동일 규칙 |
| 스크립트 콤보 패턴 | 사용 | 미사용 |
| 연계 발동 조건 | 상대에겐 미적용 | 양쪽 동일 적용 |
| 전장 슬롯 / 손패 | 3 / 5 | 4 / 7 (플레이어와 동일) |

`combat-side.js`의 `BATTLE_MODES` 한 곳에서 정의하고 `setBattleMode('pvp')`로 전환합니다.
상대 진영 접근자가 모드를 읽어 마나를 가상값/실제값으로 전환합니다.

**검증 기록.** PvE 상대 마나 99/99, PvP 상대 마나 3/3 · 슬롯 4 · 손패 7.

## 32. ⚖️ 마나가 파워를 산다 — 통합 예산

**문제.** 등급별 스탯 상한·효과 예산·마나 코스트가 **따로 놀았습니다.**
그래서 "마나를 많이 쓰는 COMMON"이 이득을 볼 방법이 없었습니다.

**결정.** 하나의 방정식으로 묶습니다.

```
지불 가능한 파워 = 기본치[등급] + 마나코스트 × 효율[등급]
사용한 파워      = 효과 점수 + 스탯 점수
```

| 등급 | 기본치 | 마나당 효율 |
|---|---:|---:|
| common | 1 | ×1.0 |
| rare | 2 | ×1.5 |
| epic | 3 | ×2.0 |
| legendary | 4 | ×2.5 |

스탯도 파워를 씁니다 — 공격력 6당 1점, 체력 12당 1점, 방어력 8당 1점.

**교정 순서가 중요합니다.** 효과를 지우기 **전에 마나 코스트를 먼저 올려** 값을 치릅니다.
이것이 "낮은 등급이 여러 효과를 갖되 마나를 많이 쓴다"는 규칙을 만듭니다.

```
1. 등급 요건 미달 효과 제거 (COMMON의 무적 등)
2. 마나 코스트를 올려 파워를 산다  ← 여기가 핵심
3. 그래도 넘치면 비싼 효과부터 제거
4. 그래도 넘치면 스탯을 깎는다
```

**검증 기록.** 동일 효과(피해+연타+화상)를 등급별로 부여했을 때

| 등급 | 마나 | 스탯 | 남은 효과 |
|---|---:|---|---|
| common | **6** | 10/20 | 피해, 화상 (연타 상실) |
| rare | 5 | 10/20 | 피해, 화상, 연타 |
| epic | 4 | 14/26 | 피해, 화상, 연타 |
| legendary | **3** | 18/30 | 피해, 화상, 연타 |

같은 효과에 common은 마나 6, legendary는 마나 3. 효율이 곧 희귀도의 가치입니다.

## 33. 연계 액션에 등급을 매기고 14종으로 늘린다

**문제.** 액션 8종 중 강함이 제각각인데 등급이 없어, LLM이 강한 액션만 고를 수 있었습니다.

**결정.** 액션마다 `tier`(1~4)를 부여하고, 등급이 높을수록 **위력 기본치를 낮춰** 균형을 맞춥니다.

| 등급 | 위력 배율 | 액션 |
|---|---:|---|
| 1 기본 | ×1.0 | manaCharge · chainDamage · shieldHeal |
| 2 준수 | ×0.85 | search · draw · **archetypeRally** · **archetypeGuard** |
| 3 강력 | ×0.7 | freeze · specialSummon · **archetypeSalvage** · **shieldBreak** · **handDisrupt** |
| 4 최상 | ×0.55 | doubleCast · **sacrificeStrike** |

**신규 6종은 카드군을 한정하는 특수 연계입니다.**

| 액션 | 효과 |
|---|---|
| `archetypeRally` | **같은 카드군** 소환수 전체 공격력 강화 |
| `archetypeGuard` | **같은 카드군** 소환수에게 도발 + 방어력 부여 |
| `archetypeSalvage` | 덱에서 **같은 카드군** 카드 회수 |
| `shieldBreak` | 상대 방어막 파괴 (방어 카드군 카운터) |
| `handDisrupt` | 상대 손패 파기 (자원 압박) |
| `sacrificeStrike` | **같은 카드군** 소환수를 제물로 대형 피해 |

`archetype*` 액션은 범용 버프가 아니라 **자기 카드군에만** 적용됩니다.
카드군 정체성을 살리는 것이 목적입니다.

프롬프트에 "3~4등급만 고르지 말 것"을 명시했습니다.

**검증 기록.** 6종 전부 실전 발동 확인. `sacrificeStrike`는 제물 1체 소모 후
tier4 보정(14×0.55=8) + 제물 공격력 8 = 16 피해로 정확히 계산됨.

## 34. 🪤 함정 카드 — 조건부 발동

**문제.** 액션이 전부 **즉발**이었습니다. 카드를 내면 바로 효과가 터집니다.
상대 행동을 읽고 반응하는 카드가 없었습니다.

**결정.** `cardType: 'trap'`을 추가합니다. 뒷면으로 세트되고 **상대가 조건을
만족할 때 자동 발동**합니다.

**발동 조건** (`trap-system.js`의 `TRAP_TRIGGERS`)

| 조건 | 설명 | 추가 값 |
|---|---|---|
| `foePlaysUnit` / `foePlaysSpell` | 상대가 해당 타입을 낼 때 | — |
| `foePlaysElement` | 상대가 특정 속성 카드를 낼 때 | `condition.element` |
| `foePlaysArchetype` | 상대가 특정 카드군 카드를 낼 때 | `condition.archetype` |
| `foePlaysKeyword` | 상대 카드가 특정 키워드를 가질 때 | `condition.keyword` |
| `foeAttacks` | 상대가 공격할 때 | — |
| `selfLowHp` | 내 체력 절반 이하 | — |

**밸런스: `TRAP_ZONE_SIZE = 3`.** 제한이 없으면 함정만 깔아두는 덱이 무적이 됩니다.

함정 효과는 **기존 스킬 어휘를 그대로** 씁니다 — 새 엔진이 필요 없습니다.
조건부라 즉발보다 싸게 책정했습니다(`trapTrigger` cost 1).

**검증 기록.** 조건 불일치(water) → 대기, 일치(fire) → 발동 후 소모,
4장 세트 시도 → 3장에서 차단.

## 35. 덱 중복 허용 + 크기 확대

**문제.** 덱에 같은 카드를 한 장만 넣을 수 있어 "종류만 다른 카드 모음"이 됐습니다.
실제 TCG는 같은 카드를 여러 장 넣어 **안정성을 사는 것**이 덱 빌딩의 핵심입니다.

**결정.**

```js
MAX_DECK_SIZE = 20        // 이전 12
RECOMMENDED_DECK_SIZE = 16 // 이전 10
MAX_COPIES_PER_CARD = 3    // 신규 — 유희왕식 3장 제한
```

`removeFromActiveDeck()`도 `filter`에서 `splice`로 바꿔 **한 장만** 뺍니다.
덱 편성 화면은 "덱 편성 중" 대신 **"덱 N장"**으로 매수를 보여줍니다.

## 36. 범용 카드 비율을 명시한다

실제 TCG는 범용이 덱의 절반 가까이 차지합니다.

**결정.** 프롬프트에 **"약 35~40%는 범용으로"**를 명시하고, 좋은 범용 카드의

## 37. 테마 보스 — 자기 카드군 덱만 쓴다

## 38. 카드 연성소 세부 커스터마이즈

**문제.** 단일 카드 생성에서 지정할 수 있는 게 컨셉 텍스트와 속성뿐이었습니다.

**결정.** `custom-overrides.js`를 신설하고 연성소에 접이식 패널을 추가했습니다.

지정 가능: 카드군 · 키워드 · 등급 · 마나 · 공/방/체 · 연계 액션·발동조건·증가방식 ·
함정 발동조건·조건값 · 원하는 효과 설명

**적용 순서가 중요합니다.**

```js
sanitizeAndClampCardData(applyCustomOverrides(rawData, readCustomOverrides()))
```

커스텀 값을 **먼저 덮어쓴 뒤** 밸런스 검증을 태웁니다. 순서가 반대면 사용자가 정한
수치가 파워 예산을 건너뛰어 밸런스가 무너집니다.

프롬프트 지시와 코드 강제를 **둘 다** 합니다 — LLM이 지시를 무시하는 경우가 있습니다.

## 39. 🎯 연계 대상 범위 — 카드군 / 속성 / 타입 / 전체

**문제.** 연계가 **같은 카드군에만** 반응해서 범용 카드는 어떤 연계에도 걸리지
않았습니다. 덱에서 겉돌았습니다.

**결정.** 카드군이 "무엇에 반응하는가"를 고릅니다 (`comboScope`).

| 범위 | 반응 대상 | 위력 | 가능해지는 덱 |
|---|---|---:|---|
| `archetype` | 같은 카드군 | ×1.0 | 카드군 덱 (기존) |
| `element` | 같은 속성 | ×0.8 | **속성 덱** |
| `cardType` | 같은 카드 타입 | ×0.8 | **소환수/주문/함정 덱** |
| `any` | 아무 아군 카드 | ×0.6 | **범용 중심 덱** |

**범위가 넓을수록 위력을 낮춥니다.** 조건이 쉬운 만큼 값을 치릅니다.

**검증 기록.** `같은 속성` 범위에서 홍련검사·범용용병·범용주문 모두 반응(물의정령은 제외),
`같은 주문 카드` 범위에서 범용주문만 반응.

## 42. 🐛 덱 중복 카드는 반드시 복제해야 한다

**문제.** AI 생성 게임이라 같은 카드를 여러 장 만들 수 없으므로, 보관함에 1장만

**3장이 전부 같은 객체를 가리켰습니다.** 한 장이 피해를 입으면 나머지도 같이 죽습니다.

**결정.** 매핑 시 복제하고 사본마다 `instanceId`(`카드id#인덱스`)를 붙입니다.
전장 소환 시에도 `instanceId`를 부여하고, 연계의 "자기 자신 제외" 판정도
`id` 대신 `instanceId`로 합니다.

**검증 기록.** 보관함 1장 → 덱 3장, 인스턴스 id `starter-1#0/#1/#2`,
1번 사본 HP 변경이 2번 사본에 영향 없음.

## 43. PvP 세션 — 덱 교환 + 시드 합의 + 치트 방어

**결정.** `pvp-session.js`가 대전 절차만 담당합니다. **네트워크 전송은 주입받습니다**
(`send` 함수) — WebRTC든 로컬 테스트든 같은 세션 코드를 씁니다.

**덱 페이로드** — 이미지 제외 시 카드 5장 + 카드군 3개 = **2.7KB**.
카드군 정의는 연계 실행에 필요한 9개 필드만 싣습니다.

**시드 합의** — 호스트가 시드를 정해 양쪽이 같은 난수로 같은 전개를 봅니다(락스텝).
`rng.js`(#28)가 이걸 가능하게 합니다.

**치트 방어** — P2P는 상대 클라이언트를 신뢰할 수 없습니다.
받은 덱을 `sanitizeAndClampCardData()`에 통과시키면 파워 예산 시스템(#32)이
**그대로 검증기 역할**을 합니다. 별도 안티치트가 필요 없습니다.

**검증 기록.** 조작된 COMMON 카드(마나1 / 999·999·999 / 무적+관통+처형+드로우5+더블캐스트)를
전송하니 **마나6 / 10·6·22 / 피해만** 남고 나머지가 전부 제거됐습니다.
루프백 핸드셰이크에서 양쪽 시드 일치, 행동 전송 정상.

**남은 것.** WebRTC 트랜스포트와 시그널링 서버. 세션 계층은 준비됐으므로
`createPvpSession({ send })`에 데이터 채널 전송 함수만 연결하면 됩니다.

## 44. 🐛 TIPO 태그 SLM — 프롬프트 형식 3중 오류와 출력 정제

**날짜:** 2026-09-01
**파일:** `js/tag-slm.js`

### 증상

TIPO를 붙였는데 시드를 **완전히 무시**했다.
`crimson swordsman, flaming katana`를 넣으면 여우, 검은 고양이,
`king of the sands`가 나왔다.

### 원인 — 3가지가 동시에 틀렸다

| 틀린 것 | 맞는 것 | 근거 |
|---|---|---|
| `tags:` / `general:` | **`tag:`** | 모델 자신의 출력이 `tag:`로 시작한다 |
| `<|extended|>` 로 종결 | **`<|input_end|>`** | `<|extended|>`는 종결이 아니라 `target:` 필드의 길이 모드 값 |
| `raw` 미지정 | **`raw: true`** | TIPO는 instruct가 아니라 순수 완성 모델. Ollama 채팅 템플릿이 덧씌워져 포맷이 깨진다 |

### 원인 4 — 어휘가 분포 밖

TIPO는 **Danbooru 어휘로만** 사고한다. `crimson swordsman` 같은 자유 영어구는
학습 분포 밖이라 그냥 버린다. `parseNaturalLanguageToDanbooru()`로 먼저
정규화해서 넣어야 한다.

```
1boy, red hair, katana, fire, armor
  → japanese armor, kimono, blue fire, holding sword, pauldrons ...   ✅ 반응함
```

### 출력을 그대로 쓰면 안 되는 이유 (실측)

1. **판권/캐릭터 누출** — `genshin impact`, `vision (genshin impact)`, `kusazuri (mahousou)`
2. **모순 태그 동시 출력** — `white hair, black hair, grey hair, red hair, blue hair`를
   한꺼번에. `closed eyes`+`blue eyes`+`green eyes`, `:d`+`:|`+`:o`.
   확률 나열일 뿐이라 그대로 주면 얼굴이 뭉개진다.
3. **메타 라인 누출** — `meta: highres`, `aspect ratio: 0.7`, `copyrights: ...`
4. **유해 태그** — `blurry`가 실제로 통과했다. Danbooru에선 서술 태그지만
   NovelAI에 긍정 프롬프트로 주면 초점 나간 그림이 나온다.

→ `cleanSlmTags()`가 넷 다 처리한다. **임의로 완화하지 말 것.**

### 파이프라인 (최종)

```
시드(자유 영어)
  → parseNaturalLanguageToDanbooru()      SLM이 알아듣는 어휘로
  → expandDanbooruTags(핵심 18개)          속성·타입 정체성 확정 (규칙이 권위)
  → TIPO 확장 → cleanSlmTags()             나머지 자리를 디테일로 (다양성)
  → 그림체 태그를 맨 앞에                    작가 or 화풍
```

**규칙 기반이 권위를 갖는다.** 카드가 무슨 속성·타입인지는 절대 흔들리면 안 되므로
뼈대는 규칙이 만들고, SLM은 남은 자리만 채운다.

## 45. 판권 태그는 차단이 아니라 **맥락 허용**. 네거티브로 보내지 않는다

**날짜:** 2026-09-01
**파일:** `js/tag-slm.js`

### 왜 전면 차단이 아닌가

처음엔 괄호 달린 태그를 전부 버렸다. 그런데 **판권 카드군**(특정 작품 테마 덱)을
만들려면 그 태그가 있어야 한다. 사용자 지적으로 3단 정책이 됐다.

| 모드 | 동작 | 쓰는 때 |
|---|---|---|
| `auto` (기본) | 카드 컨셉이 그 작품을 **실제로 언급했을 때만** 통과 | 평범한 카드에 엉뚱한 캐릭터가 섞이는 것만 막는다 |
| `always` | 전부 통과 | 판권 테마 덱 |
| `never` | 전부 차단 | 순수 오리지널만 |

`never`여도 **사용자가 직접 시드에 쓴 판권 이름은 남는다.** 정책은 SLM이 끌어오는
것만 통제한다 — 사용자가 명시적으로 요청한 것을 뒤집지 않는다.

### 🚫 차단한 판권 태그를 네거티브로 보내지 말 것

한때 `genshin impact`를 네거티브로 넘겼다. **틀렸다.**
네거티브에 넣으면 그 캐릭터만 밀어내는 게 아니라 **그 그림체 전체**를 밀어내서
결과가 오히려 나빠진다. 판권 태그는 "그리면 안 되는 것"이 아니라
"지금 카드와 무관한 것"일 뿐이다. 그냥 뺀다.

### 🐛 `(ff14)` 누출

IP 판정 정규식이 `/^(.+?)\s*\(([^)]+)\)$/` 라 **괄호 앞에 글자가 있어야** 했다.
`(ff14)`처럼 괄호만 있는 태그가 범용 카드로 새어 나갔다.
→ 괄호가 조금이라도 있으면 IP 후보로 본다 (`HAS_PAREN`).

## 46. 🐛 JUNK_TAG 정규식이 통째로 죽어 있었다

**날짜:** 2026-09-01
**파일:** `js/tag-slm.js`

배열을 `''`로 이어 붙이면서 이렇게 됐다:

```js
'[()\[\]<>|]' + '^(?:tachi-e|...)$'
// → /[()\[\]<>|]^(?:tachi-e|...)$/
//   "괄호문자 뒤에 문자열 시작"을 요구 → 영영 매치되지 않음
```

필터가 **하나도 동작하지 않았고** `blurry`가 그대로 통과해 흐린 카드가 나왔다.
성격이 다른 두 조건(문자 포함 검사 / 전체 일치 검사)을 한 정규식에 넣은 것이 원인.

→ `JUNK_CHARS`(문자 포함)와 `JUNK_TAG`(전체 일치)로 **반드시 분리**해서 둔다.

**교훈:** 정규식을 문자열 배열로 조립할 때는 앵커(`^`/`$`)의 위치를 눈으로 확인하라.
조립된 최종 패턴을 콘솔에 찍어보는 것이 가장 빠르다.

## 47. NovelAI 가중치 문법은 `{}` / `[]` 이지 `()` 가 아니다

**날짜:** 2026-09-01
**파일:** `js/tag-slm.js`

`flame (weapon)` 같은 태그를 보고 "괄호가 가중치니 벗겨야 한다"고 판단했다가
사용자 지적으로 정정했다. **`()`는 Stable Diffusion WebUI 문법이다.**

| 문법 | 도구 |
|---|---|
| `{강조}` / `[약화]` | **NovelAI** |
| `(강조)` / `[약화]` | Stable Diffusion WebUI |

그래서:

- **소괄호는 벗기지 않는다.** `flame (weapon)`은 Danbooru의 정식 동음이의
  구분자가 붙은 태그 이름이고 NovelAI도 그 형태로 학습돼 있다.
  벗기면 존재하지 않는 태그가 된다.
- **중괄호·대괄호는 막는다** (`JUNK_CHARS`). 태그에 섞여 들어오면 의도치 않은
  가중치가 걸린다. `::1.3::` 수치 가중치도 같은 이유로 막는다.

## 48. 그림체 다양성의 진짜 열쇠는 작가 태그. 못 얻으면 화풍 태그로.

**날짜:** 2026-09-01
**파일:** `js/tag-slm.js`

### 문제의 진짜 원인

"그림체가 단조롭다"를 배경·조명 태그를 흔들어 고치려 했는데, Danbooru 계열
모델에서 **그림체를 가장 강하게 좌우하는 건 작가 태그**다. 그게 비어 있으면
무엇을 흔들어도 모델의 평균 그림체로 수렴한다.

그런데 TIPO 프롬프트에 `artist: <|empty|>`를 박아 **아예 못 만들게 해놓고** 있었다.
출력의 `artist:` 라인도 메타로 취급해 버렸다. 봉인해놓고 다양성을 기대한 셈.

→ 작가를 원하면 `artist:` 줄을 **아예 넣지 않는다.** 그러면 모델이 이어쓰기로 채운다.

### 그런데 TIPO의 작가 출력은 신뢰할 수 없다

실측: 4번 중 1번만 나왔고 그마저 `l an'erure` 같은 깨진 문자열이었다.
→ `isPlausibleArtistTag()`로 형태 검증을 걸고, **못 얻으면 화풍 태그로 폴백**한다.

`ART_STYLE_POOL`은 특정 작가를 흉내 내지 않으면서 화풍·질감·조명을 바꾼다.
실패해도 그림이 망가지지 않는 것이 장점.

| 모드 | 동작 |
|---|---|
| `slm` (기본) | TIPO 작가 → 실패 시 화풍 태그 |
| `style` | 화풍 태그만 (가장 안정적) |
| `custom` | 사용자 지정 목록에서 카드당 **1명** |
| `off` | 없음 (모델 기본 그림체) |

**카드당 작가/화풍은 1묶음만.** 여러 개를 섞으면 화풍이 충돌해 뭉개진다.

⚠️ `ART_STYLE_POOL`에 `monochrome`/`greyscale` 계열을 넣지 말 것.
   `monochrome accents`를 넣었다가 물 속성 카드가 흑백으로 나올 뻔했다.

## 50. 🐛 카드팩이 카드군 속성 정책을 무시했다

**날짜:** 2026-09-01
**파일:** `js/card-pack.js`, `js/archetype-service.js`

### 증상

`[심연의 그림자단]`(어둠 / mono)에 🔥화염 카드와 ⚡번개 카드가 섞여 나왔다.
mono 정책이 있는데도 지켜지지 않았다.

### 원인 — 순서가 거꾸로였다

```
card-pack.js:205   팩 속성 목록에서 element 랜덤 선택   ← 카드군을 알기 전!
       ↓
LLM에게 "Element: fire" 로 생성 요청
       ↓
LLM 답변: "이 카드는 [심연의 그림자단] 소속"          ← 어둠/mono 카드군
       ↓
card-pack.js       element: element  ← 팩이 뽑은 fire를 그대로 저장
```

`coerceCardElement()`는 **`card-forge.js`(단일 생성)에만** 걸려 있었고
카드팩 경로에는 아예 없었다. 팩은 카드군보다 속성을 먼저 정하는 구조라
교정이 더 필요한 쪽인데도 빠져 있었다.

### 수정

카드군이 확정된 직후(`themeObj` 결정 후) 교정한다.

**⚠️ 반드시 이미지 생성보다 먼저.** 안 그러면 데이터는 어둠인데 일러스트는
화염으로 그려진 카드가 나온다.

```js
const elementFix = coerceCardElement(themeObj, element);
if (elementFix.changed) element = elementFix.element;
// ↓ 그 다음에 MOCK_PACK_IMAGES / generateNovelAIImage
```

### 기존 카드 보수

`repairArchetypeRecords()`의 카드 루프에 속성 교정을 추가했다.
부팅 때마다 돌므로 **새로고침만 하면 기존 카드가 자동으로 고쳐진다.**

미리 보려면 콘솔에서:

```js
await repairArchetypeRecords({ dryRun: true })
```

> 일러스트는 이전 속성으로 그려진 채 남는다. 그림까지 맞추려면 카드를 다시 생성해야 한다.
> 이건 의도적이다 — 이미지 재생성은 NovelAI 호출 비용이 들고, 사용자가 결정할 일이다.

### 교훈

**속성을 정하는 지점이 여러 곳이면 교정도 여러 곳에 필요하다.**
새 카드 생성 경로를 추가하면 `coerceCardElement()`를 반드시 끼우세요.
현재 걸려 있는 곳:

| 경로 | 파일 |
|---|---|
| 단일 카드 생성 | `card-forge.js` (`finalElement`) |
| 부스터 팩 | `card-pack.js` (`themeObj` 확정 직후) |
| 기존 카드 보수 | `archetype-service.js` (`repairArchetypeRecords`) |

## 51. 카드 이름은 타입이 결정한다 — 끝 단어로 판정

## 52. 모달은 헤더·푸터 고정 + 본문만 스크롤

**날짜:** 2026-09-01
**파일:** `index.html`, `styles.css`

설정 항목이 늘면서 모달이 화면을 넘어가 **저장 버튼에 닿지 못했다.**

```
바깥: fixed inset-0 flex items-center justify-center
안쪽: flex flex-col + style="max-height:90vh; max-height:90dvh"
      ├ 헤더  shrink-0
      ├ 본문  flex-1 min-h-0 overflow-y-auto overscroll-contain   ← 여기만 스크롤
      └ 푸터  shrink-0
```

`min-h-0`이 없으면 flex 자식이 줄어들지 않아 스크롤이 안 생긴다. `dvh`는 모바일
주소창 대응이고, 지원 안 하는 브라우저를 위해 `vh`를 먼저 쓴다.

### ⚠️ `items-center` + `overflow-y-auto`는 함정

내용이 화면보다 길면 **위쪽이 잘려 스크롤로도 닿지 못한다.**
자식에 `my-auto`를 주면 여유가 있을 땐 가운데, 넘칠 땐 정상 스크롤이 된다.
(boss-forge-modal, keyword-info-modal에 적용)

## 53. 반응형 — 실제로 발견된 것들

**날짜:** 2026-09-01
**파일:** `index.html`, `styles.css`

375px에서 실측한 문제와 해법:

| 증상 | 원인 | 해법 |
|---|---|---|
| 탭이 "배틀 아 / 레나"로 쪼개짐 | 좁은 폭에서 줄바꿈 | `whitespace-nowrap` + `shrink-0`, 넘치면 **가로 스크롤** |
| "도전할 보스:"가 한 글자씩 세로 | 라벨이 압축됨 | `shrink-0 whitespace-nowrap`, select에 `min-w-0` |
| 보스 연성 버튼 화면 밖 | 라벨이 김 | `xs:` 미만에서 짧은 라벨로 교체 |

### 가로 스크롤 오진 주의

`documentElement.scrollWidth > clientWidth`로 판정하면 **세로 스크롤바 폭(≈18px) 때문에
항상 참이 나온다.** 실제 판정은 이렇게:

```js
de.scrollLeft = 9999;
const hasOverflow = de.scrollLeft > 0;
de.scrollLeft = 0;
```

이 오진 때문에 멀쩡한 장식 요소(`-right-20 w-64`, 부모에 이미 `overflow-hidden` 있음)를
범인으로 착각했다.

### `xs` 브레이크포인트 추가

기본 Tailwind는 `sm`(640px)이 최소다. 그보다 좁은 폰을 위해 `xs: 400px`를 추가했다.

### styles.css 캐시

`no-scrollbar`를 추가했는데 적용이 안 돼 한참 헤맸다. 서버는 `no-cache`를 보내고
있었지만 **브라우저 메모리 캐시**가 옛 파일을 들고 있었다.
CSSOM에 규칙이 실제로 들어왔는지로 확인하는 게 가장 빠르다:

```js
[...document.styleSheets].flatMap(s => [...s.cssRules])
  .filter(r => r.selectorText?.includes('no-scrollbar'))
```

## 54. PvP — 상대를 "보스 자리"에 앉힌다

**날짜:** 2026-09-01
**파일:** `js/pvp-battle.js`(신규), `js/pvp-ui.js`(신규), `js/battle-engine.js`

### 왜 대칭 엔진으로 다시 쓰지 않았나

`battle-engine.js`(약 1400줄)는 완전히 PvE 형태다. 대칭 엔진으로 재작성하면
잘 돌아가던 PvE 밸런스·연출이 전부 위험해진다.

그래서 구조를 바꾸지 않고 **보스 자리를 원격 플레이어가 차지**하게 했다.

```
내 화면 :  나 = player 진영  /  상대 = boss 진영
상대 화면:  상대 = player 진영  /  나 = boss 진영
```

서로 거울처럼 본다. 내 "플레이어 턴"이 상대에겐 "보스 턴"이라 턴이 자연히 교대된다.
`combat-side.js`의 `BATTLE_MODES.pvp`가 애초에 이걸 노리고 만들어져 있었다.

### 순환 import를 피한 방향

- 엔진 → 브릿지: `import`
- 브릿지 → 엔진: **콜백** (`registerPvpHandlers`)

### 동작 확인된 것 (2탭 실전 테스트)

| 항목 | 결과 |
|---|---|
| 방 만들기 / 코드 참가 | ✅ |
| WebRTC 연결 (server.py 시그널링 중계) | ✅ |
| 덱 교환 + 밸런스 검증 | ✅ |
| 시드 합의 | ✅ 양쪽 동일 |
| 카드 플레이 동기화 | ✅ 상대 화면에 그대로 재현 |
| 공격 동기화 | ✅ 26 → 6 정확히 반영 |
| 턴 교대 | ✅ |
| 상대 전장 초기화 | ✅ (PvE 보스 하수인이 남던 버그 수정) |

### ⚠️ 남은 문제 — 피해 결과가 어긋난다

같은 카드가 양쪽에서 **다르게 해석된다.**

```
게스트 화면: 내 소환수 전투의 함성 → 상대에게 20 + 더블캐스트 20 = 40
호스트 화면: 같은 카드를 보스가 냄  → 플레이어가 8 피해
```

원인: `playCard()`와 `playBossCard()`가 **근본적으로 다른 해석 경로**다.

- `playCard()`   → `triggerBattlecry()` 발동, 스킬 원본 수치
- `playBossCard()` → 전투의 함성 **발동 안 함**, 주문 피해에 ×0.7 감산,
                     보스 전용 콤보(`triggerBossArchetypeCombo`) 사용

PvE에서는 **의도된 차이**다 (보스는 스크립트 패턴으로 싸운다). 하지만 PvP에서는
락스텝이 깨진다.

**해결 방향:** `playCard()`의 카드 해석부를 진영 무관 함수로 뽑아내고,
PvP 모드일 때 `playBossCard()`가 그 함수를 쓰게 한다.
PvE 경로는 `isPvp()`로 갈라 그대로 둔다 — 밸런스를 건드리면 안 된다.

### 그 밖에 PvP에서 꺼야 할 PvE 연출

- 보스 대사(`BOSS VOICE`), 광폭화(`[광폭화] 보스가 격노하여...`)
- 로그 문구 "👹 보스 고유 전술 카드" → 상대 플레이어 표기로

## 55. PvE / PvP 완전 분리 — 탭도, 해석 경로도

**날짜:** 2026-09-01
**파일:** `js/battle-engine.js`, `js/pvp-ui.js`, `index.html`

### 앞선 시도가 왜 틀렸나 ([#54](#54) 정정)

"보스 자리에 원격 플레이어를 앉힌다"로 만들었다. 구현은 빨랐지만
**분리해달라는 요구와 정반대**였고, 실제로 문제가 났다:

- 상대가 `흑염룡의 사도 바알` 같은 PvE 보스로 보였다
- 보스 대사·광폭화·스크립트 콤보가 PvP에서 튀어나왔다
- `playBossCard()`가 PvE 전용이라 **같은 카드가 양쪽에서 다르게 해석**됐다
  (내 화면 40 피해 / 상대 화면 8 피해)

### 지금 구조

| | PvE | PvP |
|---|---|---|
| 탭 | `배틀 아레나` | **`온라인 대전`** (별도) |
| 상대 | 보스 (마나 없음, 스크립트 패턴) | 듀얼리스트 (같은 마나 규칙) |
| 카드 해석 | `playBossCard()` | **`playFoeCardPvp()`** |
| 전투의 함성 | 발동 안 함 (의도된 차이) | 발동 |
| 주문 피해 | ×0.7 감산 | 감산 없음 |

### 거울 해석 (`playFoeCardPvp`)

`applyPlayerSkillEffects`가 `game`/`helpers`를 주입받게 돼 있어서,
**진영만 뒤집은 뷰**를 넘기면 같은 규칙으로 해석된다.

```js
makeMirroredGame()     // bossMinions ↔ playerMinions, playerHp → 상대 HP ...
makeMirroredHelpers()  // dealDamageToBoss → applyDirectDamageToPlayer
                       // setBossStatus → 내 상태이상
```

PvE 경로는 **한 줄도 건드리지 않았다.** 밸런스가 걸려 있기 때문이다.

## 58. 전장은 탭 사이를 **옮겨 다닌다** (마크업 복제 금지)

**날짜:** 2026-09-01
**파일:** `js/battle-arena.js`(신규), `index.html`

### 요구 정정

[#55](#55)에서 "온라인 대전 탭"을 만들었지만 **매칭 UI만** 거기 두고
대전이 시작되면 `배틀 아레나` 탭으로 보냈다. 요구는 그게 아니었다:

- `배틀 아레나` — **PvE 보스전만**
- `온라인 대전` — 매칭 **그리고 PvP 전투까지**

### 왜 마크업을 복제하지 않았나

전장 마크업(약 220줄)을 탭마다 한 벌씩 두면 `player-hand`, `battle-logs`,
`boss-container` 같은 **id가 두 벌**이 된다.
`document.getElementById`는 먼저 나온 하나만 집으므로,
renderBattleUI()가 숨겨진 쪽을 갱신하고 **화면은 조용히 안 바뀐다.**
찾기 아주 어려운 버그가 된다.

→ 노드 **하나**를 슬롯 사이로 옮긴다. id는 언제나 한 벌뿐이다.

```
tab-battle  #battle-arena-slot   ←→   tab-versus  #versus-arena-slot
                        #battle-arena (이 노드가 이동)
```

- 비워진 탭에는 "대전은 온라인 탭에 있습니다" 안내를 넣는다 (빈 화면 방지)
- 옮긴 뒤 `lucide.createIcons()`를 다시 불러야 아이콘이 살아난다

### PvE 문구 갈아 끼우기

"보스 HP", "보스의 전장", "BOSS VOICE"가 PvP에서 그대로 나오면 몰입이 깨진다.
복제하지 않으므로 **텍스트만** 바꾼다 — `.foe-word` 클래스를 달아두고
`applyArenaMode(pvp, foeName)`이 갈아 끼운다. 보스 대사 말풍선은 통째로 숨긴다.

### 대전 중 준비 영역

매칭 UI와 프로필 편집기는 대전이 시작되면 `#versus-setup`째로 숨긴다.
전투 중에 아바타를 고칠 일은 없고, 전장이 화면 위로 와야 한다.
대신 `내 이름 VS 상대 이름 · 방 코드` 바를 띄운다.

## 59. 🐛 설명문이 실제 수치와 달랐다 ("200 피해")

**날짜:** 2026-09-01
**파일:** `js/config.js`

EPIC 카드에 `방어막을 무효화하고 200 피해를 준다`가 찍혀 있었다.

`skill.damage`는 등급 상한으로 **클램프되고 있었다** (24). 문제는 설명문이었다.
`sanitizeAndClampCardData`는 설명문의 `%` 표기만 정리하고 **숫자는 손대지 않았다.**
그래서 카드는 200이라 적고 실제로는 24가 나갔다. 플레이어에게 거짓말을 한 셈이고
밸런스가 무너진 것처럼 보였다.

→ `syncDescriptionNumbers()`가 클램프 **후에** 설명문 숫자를 실제 값과 맞춘다.

```
피해 200 → 24 ... "본 턴의 공격 시 방어막을 무효화하고 24 피해를 준다."
```

⚠️ **피해·방어막·회복 단어에 바로 붙은 숫자만** 바꾼다.
"체력 35 이하일 때" 같은 조건문의 숫자를 건드리면 효과 설명이 망가진다.
그 밖의 세 자리 이상 숫자는 표기만 두 자리로 눌러 오해를 막는다.

## 62. 대상 선택 — 공격 대상과 소환 위치

**날짜:** 2026-09-01
**파일:** `js/targeting.js`(신규), `js/battle-engine.js`

카드 설명은 "적 하나를 지정해"처럼 읽히는데 실제로는 아무것도 못 골랐다.

### 공격 대상

고를 수 있는 대상이 둘 이상이면 선택 모드로 들어간다.
도발이 있으면 도발만 유효 — 규칙은 그대로다. 대상이 하나뿐이면 예전처럼 즉시 처리한다.

- `data-target-key` 속성으로 대상을 표시 (`foe:0`, `face`)
- 유효한 곳은 링+펄스, 나머지는 흐리게
- Esc로 취소

### 소환 위치

**0번 자리가 적의 공격을 먼저 받는다** — 위치가 곧 전술이다.

- 빈 슬롯 클릭 → 그 자리에 배치
- 카드 왼쪽 가장자리의 얇은 띠 클릭 → **그 카드 앞에** 끼워 넣기
  (빈 슬롯만으로는 뒤에 붙이는 것밖에 못 한다)
- 아무 것도 지정 안 하면 예전처럼 맨 뒤 — 매번 묻지 않는다

### ⚠️ PvP는 고른 것까지 보내야 한다

대상·위치를 안 보내면 상대는 자기 기준 최전방을 때리고 전열도 달라져
**락스텝이 깨진다.**

```js
sendPvpAction({ kind: 'attack',   slotIdx, targetKey })
sendPvpAction({ kind: 'playCard', instanceId, card, slot })
```

### 아직 안 된 것 — 효과 대상 지정

"적 하나를 얼린다" 같은 **효과**의 대상은 여전히 자동이다.
스킬이 `{ damage, freeze, ... }` 수치 필드만 갖고 있고 "몇 명을, 어느 진영을
고르는가"라는 **대상 메타데이터가 없다.** 그걸 먼저 스키마에 넣어야 한다
(예: `target: 'foeMinion' | 'allyMinion' | 'any' | 'all'`).

## 64. 효과 대상 스키마 — 범위가 곧 파워다

**날짜:** 2026-09-01
**파일:** `js/effect-targets.js`(신규), `js/config.js`, `js/skill-effects.js`

### 스키마

스킬에 `{ damage, shield }` 같은 **수치 필드만** 있어서 "누구를, 몇을" 고르는지
알 수 없었다. 이제 대상 메타데이터를 갖는다.

```js
{ targetSide: 'foe|ally|self|any', targetScope: 'single|multi|all|random', targetCount: 1..3 }
```

구버전 `isAoeSpell`은 `{ side:'foe', scope:'all' }`로 읽힌다. 저장된 카드는 그대로 돈다.

### ⚠️ 대상이 늘면 반드시 예산에 반영해야 한다

안 하면 "적 전체 20 피해"가 "적 1체 20 피해"와 **같은 값**으로 취급된다.

| 범위 | 배수 |
|---|---|
| 단일 | 1.0 |
| 2체 | 1.5 |
| 3체 | 2.0 |
| 전체 | 2.2 |
| 무작위 | 0.8 (지정이 아니라 약하다) |

`전체`를 2.0이 아니라 2.2로 둔 이유: 광역은 판을 통째로 정리해 단순 2배 이상의 값을 한다.

**대상과 무관한 효과에는 곱하지 않는다.** 내 방어막은 상대가 몇이든 하나다.
곱하는 것은 `damage · heal · statusEffect · multiHit · lifestealPercent` 뿐이다.

### 예산 초과 시 — 지우기 전에 좁힌다

`enforcePowerBudget` 순서에 **2-b 단계**를 넣었다.

```
1. 등급 미달 효과 제거
2. 마나 코스트 인상
2-b. 🎯 대상 범위 축소 (전체 → 3체 → 2체 → 단일)   ← 신규
3. 비싼 효과 제거
4. 스탯 삭감
```

효과를 통째로 지우는 것보다 훨씬 덜 파괴적이다.

> ⚠️ `enforcePowerBudget`의 `usedPower()`와 `evaluateCardPower`는 **같은 식**을 써야 한다.
> 한쪽만 배수를 빠뜨리면 "예산 통과"로 저장해놓고 카드 상세에는 "초과"로 뜬다.

### 런타임

- `needsTargetPick(skill)`이 참이면 카드를 낼 때 대상 선택 모드로 들어간다
- 다중이면 `0/2 → 1/2`로 세어 가며 받는다. 같은 대상 중복 선택은 막는다
- 소환수에 상태이상을 걸면 `entity.statuses`를 만들어 붙인다 (기존에는 본체만 가능했다)
- **PvP는 고른 대상까지 전송한다** (`picked`). 안 보내면 상대 화면에서 다른 대상이 맞는다

## 66. 건축물 패시브는 **등급 제한을 면제**하고, 속성별로 다르게 만든다

**날짜:** 2026-09-01
**파일:** `js/config.js`, `js/card-forge.js`, `js/card-pack.js`

"건축물은 매 턴 효과가 잘 적용되나?"를 확인하다 **네 가지 구멍**을 찾았다.
`triggerStructureEndTurnPassives()` / `triggerStructureStartTurnPassives()`
자체는 정상이었다 — 문제는 전부 **생성 쪽**이었다.

### (1) 커먼 건축물은 패시브가 통째로 삭제됐다

`EFFECT_COSTS.passiveEffect`의 `minRarity`가 `rare`라서
`enforcePowerBudget()` 1단계가 커먼 건축물의 패시브를 지웠다.
건축물은 `attack: 0`이므로 패시브가 없으면 **매 턴 아무 일도 안 하는 백지 카드**가 된다.

→ `cardType === 'structure'`이면 등급 제한을 건너뛴다.
소환수에 붙는 지속 패시브는 여전히 rare 이상이다 — 건축물만 면제다.

3단계(예산 초과 시 비싼 효과부터 제거)에서도 제외한다. cost 3이라
정렬상 거의 1순위로 잘려 나갔다. 대신 4단계에서 스탯을 깎아 값을 치른다
(건축물은 HP가 ×1.3이라 여유가 있다).

### (2) 잘려나간 효과가 설명문에 유령으로 남았다

설명문 교정은 `sanitizeAndClampCardData` **3단계**인데
효과 제거는 **4단계**(`enforcePowerBudget`)다. 순서 때문에
"매 턴 마나 +1 공급"이라 적힌 커먼 건축물의 패시브가 조용히 삭제되어도
문장은 그대로 남았다. 카드가 거짓말을 한다.

→ 예산에서 제거된 효과가 설명문에 **실제로 언급되어 있을 때만**
`describeSkillFromData()`로 다시 만든다 (`EFFECT_DESC_PATTERNS`).
언급이 없으면 LLM이 쓴 플레이버를 굳이 버리지 않는다.

⚠️ 이건 건축물만의 문제가 아니다. 커먼 소환수의 "2턴간 무적이 된다"도
같은 이유로 유령 문장이었다.

### (3) 모든 건축물이 똑같이 동작했다

생성 경로 두 곳이 `{ manaPerTurn: 1, endTurnShield: caps.shieldValue[0] }`를
**하드코딩**했다. 화염 첨탑이든 세계수든 전부 같았다.
게다가 엔진이 지원하는 `endTurnAoeShield` / `endTurnAoeHeal`은
**아무도 생성하지 않아 죽은 코드**였다 (스타터 2장 예외).

→ `buildStructurePassive(element, rarity)` 한 곳으로 모았다.

| 속성 | 패시브 |
|---|---|
| 🔥 화염 | 매 턴 마나 +1 (템포) |
| 💧 물 | 방어막 + 자기 내구도 수리 |
| ⚡ 번개 | 마나 +1 & 얇은 방어막 |
| ✨ 신성 | 본체 체력 회복 |
| 🌑 어둠 | 두꺼운 방어막 |
| 🌿 자연 | 회복 + 방어막 절반씩 |

⚠️ 파워 예산은 `passiveEffect`를 **내용과 무관하게 일괄 3점**으로 친다.
그래서 속성마다 총량을 비슷하게 맞춰야 한다 — 큰 손잡이 하나, 또는 절반짜리 둘.
손잡이를 더 얹으면 공짜로 강해진다.

### (4) 🐛 가장 컸던 것 — AI 경로는 패시브를 아예 안 넣었다

`card-forge.js`의 **AI 경로**(`skillObj`)에는 `passiveEffect`가 없었다.
프롬프트에 그 필드가 없으니 LLM도 만들지 않았다.
즉 **AI로 만든 건축물은 전부** 공격 0 + 매 턴 무효과인 순수한 벽이었다.
폴백(오프라인) 경로에만 패시브가 있어서 "가끔 되는" 것처럼 보였다.

→ 속성 교정(`coerceCardElement`) **뒤에** 패시브를 주입한다.
앞에 두면 어둠 카드군에 화염 패시브가 붙는다 ([#50](#50)과 같은 이유).

**설명문은 엔진이 쓴다.** 패시브 내용을 LLM이 정하지 않으므로
`describeStructurePassive()`로 덮어쓴다. LLM 플레이버를 남기면
"적을 불태운다" 같은 실제로는 일어나지 않는 문장이 카드에 남는다.

## 67. 카드군에 **플레이스타일**을 두고, 건축물 패시브는 속성이 아니라 그것을 따른다

**날짜:** 2026-09-01
**파일:** `js/archetype-identity.js`, `js/archetype-service.js`, `js/config.js`,
`js/battle-engine.js`, `js/card-forge.js`, `js/card-pack.js`

### 문제: #66의 속성별 패시브는 자유도를 죽였다

[#66](#66)에서 건축물 패시브를 속성으로 분기했다(화염=마나, 물=방어막…).
하드코딩을 다른 하드코딩으로 바꾼 것이라 오히려 나빠졌다.
**속성이 패시브를 결정하면 LLM이 개입할 여지가 없다.**

되돌리되 그냥 없애지는 않았다. 판단 주체를 바꿨다:
**LLM 지정 > 카드군 플레이스타일 폴백**. 속성은 더 이상 패시브를 정하지 않는다.

### 🎭 플레이스타일 — 카드군의 "어떻게 이기는가"

기존의 속성 정책·고유 연계는 **카드 한 장**의 성격만 정했다. 그래서 같은
카드군에 1마나 잡졸과 6마나 거신이 섞이고, 건축물·함정·마법은 카드군과
무관한 범용 효과를 달았다.

`ARCHETYPE_PLAYSTYLES`는 카드군 전체의 **덱 설계도**다. 6종:

| 키 | 이름 | 어떻게 이기는가 |
|---|---|---|
| `turtle` | 방어 버티기 | 체력·방어막으로 버티다 역습 |
| `swarm` | 저코스트 전개 | 1~3마나를 한 턴에 여러 장 |
| `control` | 고코스트 장악 | 무겁고 강한 카드로 후반 압도 |
| `ace` | 에이스 서포트 | 강한 소환수 하나를 여러 카드가 지킴 |
| `burn` | 본체 직격 | 소환수 무시, 본체를 태움 |
| `toolbox` | 대응 함정 | 상대 수를 읽고 되받아침 |

각 스타일은 `costBias`(마나 커브) · `favor`/`avoid`(효과 취향) ·
`typeGuide`(소환수/마법/건축물/함정별 지침)를 갖는다.

**유저에게는 노출하지 않는다.** 카드 텍스트에 "이 카드군은 전개형"이라고
적히면 설정이 새어 나온 것처럼 보인다. LLM 가이드 전용이다.

**정하는 주체는 LLM이다.** `themePlaystyle`로 직접 고른다. 값이 없을 때만
`inferPlaystyle()`이 연계 액션 → 이름/설명 어휘 순으로 추론한다.

⚠️ `inferPlaystyle`의 액션 문자열은 `archetype-combos.js`의
`ARCHETYPE_COMBO_ACTIONS` 키와 **정확히** 같아야 한다.
한 번 `guard`/`summon`/`negate` 같은 없는 이름을 써서 전부 기본값으로 떨어졌다.

### 🏛️ 패시브 두 종류 — 등급으로 가른다

유저 지적: "매 턴 올리는 게 사기면 고등급으로 한정하고, 대신
'이 카드가 전장에 있으면 올라간다' 같은 걸 쓰면 된다."

| 종류 | 성격 | 등급 |
|---|---|---|
| 매 턴 누적형 | 턴마다 쌓인다. 오래 살수록 기하급수 | **epic 이상** |
| 오라 | 쌓이지 않는다. 부서지면 즉시 사라진다 | 모든 등급 |

`PER_TURN_MIN_RARITY = 'epic'`. 커먼/레어 건축물은 오라를 쓴다.
그래서 낮은 등급 건축물도 할 일이 있다.

오라는 범위를 좁히면 값을 더 크게 준다 (`AURA_SCOPES`의 `mult`).
`archetype` 범위 오라는 **그 카드군 덱을 짜게 만드는 강력한 동기**가 된다.

### ⚠️ 이건 DECISIONS #4가 금지한 것이 아니다

[#4](#4)는 "카드군 스탯 시너지"를 금지했다. 그건 `evaluateFieldSynergy()`가
**전개 수만으로 공짜로** 붙이던 오토체스식 종족 버프였다.

오라는 다르다:
- 카드 한 장과 마나를 **지불**한다
- 건축물이 **부서지면 사라진다**
- 파워 예산에 `aura`(cost 2)로 **계상**된다

유희왕의 지속마법/필드마법에 해당한다. #4의 금지는 여전히 유효하다 —
`evaluateFieldSynergy()`는 지금도 `bonusAtk`을 만들지 않는다.

### ⚠️ 오라는 절대 저장하지 마세요

`entity.attack`에 더해 저장하면 건축물이 죽어도 보너스가 남고, 오라 두 장 중
하나가 부서질 때 어느 쪽 몫인지 알 수 없다. **항상 읽는 시점에 계산한다**
(`auraAttackBonus()` / `auraDefenseBonus()` / `auraDamageReduction()`).

표시 공격력(`displayAtk`)도 같은 식을 쓴다. 안 그러면 카드에 12라 적혀
있는데 15가 나간다.

### 🐛 곁가지로 고친 것 — 아군 소환수는 수비력이 무효였다

`foeMinionAttack`이 `t.currentHp -= bm.attack`로 직접 깎았다.
내가 공격할 때는 `damageEntity`가 수비력을 적용하는데 **방어할 때는
아무 일도 하지 않는** 비대칭이었다. `hitPlayerMinion()`으로 묶어
양방향 모두 `damageEntity`를 지나게 했다.

**검증.** 공격 20 / 자체 수비 3 / 오라 방어 4 → 실제 피해 13, 로그 "방어 7 흡수".

### 🐛 프롬프트가 직전 카드의 카드군을 보고 있었다

`currentCardTheme`은 **생성이 끝난 뒤에** 대입된다. 프롬프트를 만드는 시점에는
직전 카드의 카드군이 들어 있다. 유저가 고른 카드군은
`readCustomOverrides().themeId`로 읽어야 한다.

## 69. 카드 타입마다 **자기 예산**을 갖는다 (그리고 예산이 코스트를 내리기도 한다)

**날짜:** 2026-09-01
**파일:** `js/config.js`, `js/archetype-service.js`, `js/card-forge.js`, `js/card-pack.js`

### 문제: 네 타입이 예산 하나를 공유했다

`affordablePower(rarity, cost)`가 타입을 몰랐고, `statPower`도 소환수 기준
단가 하나만 썼다. 그런데 마법·함정은 스탯이 0이라 **예산 전부가 효과로** 갔다.

같은 등급·같은 마나에서 **효과에 쓸 수 있는 여유**가 이렇게 벌어졌다:

| 등급/마나 | 소환수 | 건축물 | 마법 | 함정 |
|---|---|---|---|---|
| 커먼 1마나 | **0.4** | 1.2 | 3.2 | 3.2 |
| 레어 2마나 | **1.7** | 3.0 | 6.2 | 6.2 |
| 레전더리 3마나 | **4.0** | 6.5 | 11.6 | 11.6 |

최대 8배다. 결과:
- **소환수**는 자기 스탯에 예산을 다 써서 효과를 못 달았고, 달려면 코스트가
  올라갔다 → "저코스트 카드가 사라지는" 원인
- **마법·함정**은 효과를 무제한 쌓았다
- **건축물**은 체력(hp×1.3)이 예산을 먹어 패시브를 달 여유가 없었다 →
  [#66](#66)에서 예외 처리(`if (isStructure) continue`)로 가렸던 그 증상

### 해결: TYPE_POWER — 손잡이 두 개

```
              budgetMult   statDivisor(hp)   왜
소환수 unit      1.00            10          기준. 스탯+효과, 매 턴 공격
건축물 structure 0.90            20          공격 못 함 → 체력이 싸다
마법   spell     0.70            —           일회용, 판에 남지 않음
함정   trap      0.85            —           조건부, 안 터질 위험을 보상
```

조정 후 격차는 **1.3~2.0배**로 좁혀졌다.

⚠️ 수치를 만질 때는 **효과 여유**(예산 − 스탯)를 보세요.
예산만 보면 스탯이 0인 마법·함정이 실제로 얼마나 강해지는지 놓칩니다.

### 🪤 trapTrigger는 cost 0이다

발동조건은 **제약이지 능력이 아니다.** 예전에는 cost 1을 청구했다.
그러면 조건부 함정이 즉발 마법보다 불리해지고, 그걸 보상하려 함정 예산
배수를 올리면 총량이 부풀었다 (0.95까지 올려야 겨우 마법과 비슷해졌다).

**조건부의 보상은 `TYPE_POWER.trap.budgetMult` 한 곳에서만 준다.**
trapTrigger에 값을 다시 매기면 그 보상이 상쇄된다.

### 🐛 예산이 코스트를 **내리기도** 한다 (2-a 단계)

예전에는 예산이 코스트를 **올리기만** 했다. 그래서 생성기가 무작위로
높은 코스트를 뽑으면 그대로 남았고, 실측으로 이런 카드가 나왔다:

> `unit common 6마나 예산 10 사용 4.3 [무효과]`

6마나 커먼 바닐라. 선택지가 아니라 死카드다.

이제 `usedPower() <= affordablePower(cost - 1)`인 동안 코스트를 내린다.
바닥은 `RARITY_BALANCE_CAPS[rarity].costRange[0]` — 레전더리가 1마나로
떨어지지는 않는다.

⚠️ **저등급 고코스트 카드를 없애는 게 아니다.** 효과가 좋아서 값을 치르는
카드는 `usedPower`가 높으므로 내려가지 않는다. 검증:

| 입력 | 결과 |
|---|---|
| 효과 없는 커먼 소환수 6마나 | → **2마나** (값을 치를 것이 없다) |
| 효과 3개 커먼 소환수 6마나 | → **5마나** 유지, 효과도 유지 |

### 건축물 예외 처리를 **없앴다**

[#66](#66)에서 넣은 `if (isStructure && e.key === 'passiveEffect') continue`
두 곳을 제거했다. 타입별 예산이 근본 원인을 고쳤기 때문이다.

**검증.** 등급 4 × 마나 2 × 플레이스타일 6 = **48개 조합**을 각 등급의
**최대 스탯**(최악 조건)으로 돌려 패시브 삭제 0건.

⚠️ 여기에 타입 예외를 다시 추가하고 싶어지면, 먼저 `TYPE_POWER` 쪽이
잘못된 게 아닌지 보세요. **예외는 거의 항상 예산 모델의 오류 신호입니다.**

### rebalanceExistingCards가 마나 과다도 잡는다

`if (!overBudget && !illegal) continue`로 **예산 초과만** 고쳤다.
코스트 하향이 생긴 뒤로는 반대 방향도 고칠 수 있으므로,
`sanitizeAndClampCardData`를 먼저 돌려 **실제로 달라지는 것이 있을 때만**
기록하도록 바꿨다 (전부 통과시키면 멀쩡한 카드까지 설명문이 다시 쓰인다).

콘솔에서 `rebalanceExistingCards({dryRun:true})`로 미리 볼 수 있다.
되돌리기는 `restoreCardsBackup()`.

### 남은 것

예산은 효과의 **개수**를 값매기고, **크기**는 `RARITY_BALANCE_CAPS`가
등급별로 제한한다. 그래서 "20 피해 마법"과 "8 피해 마법"이 같은 1점이다.
의도된 분업이지만, 크기까지 예산에 넣으려면 `EFFECT_COSTS`를
값 구간별로 쪼개야 한다 — 지금은 하지 않았다.

## 70. 효과의 **크기**도 예산에 넣는다 (그리고 초과하면 지우기 전에 깎는다)

**날짜:** 2026-09-01
**파일:** `js/config.js`

### 문제

[#69](#69)에서 타입별 예산을 나눴지만 `EFFECT_COSTS`는 여전히 효과의
**존재**만 값매겼다. 그래서 **"28 피해"와 "8 피해"가 똑같이 1점**이었다.
크기는 `RARITY_BALANCE_CAPS`가 등급별 상한만 걸었을 뿐, 같은 등급 안에서
상한을 꽉 채운 카드와 하한만 쓴 카드가 같은 값을 냈다.

### 해결: EFFECT_MAGNITUDE

```
실제비용 = 기본비용 × max(1, 크기 / perUnit)
```

| | perUnit | 커먼 하한 → 상한 | 레전더리 상한 |
|---|---|---|---|
| damage | 10 | 8→1.0 / 12→1.2 | 28→**2.8** |
| shield | 8 | 6→1.0 / 10→1.3 | 26→**3.3** |
| heal | 8 | 6→1.0 / 10→1.3 | 26→3.3 |
| statusEffect | 16 | 8×2턴→2.0 | 12×3턴→**4.5** |
| drawCards | 1.5 | 1장→2.0 | 3장→**4.0** |

⚠️ **perUnit은 "커먼 등급 중간값 ≈ 1단위"가 되도록 맞췄다.**
(커먼 피해 중간값 10 → 10/10 = 1단위 → 비용 1 = 예전과 동일)
이래서 기존 밸런스 곡선을 유지한 채 **등급 내 편차만** 반영된다.
perUnit을 낮추면 모든 카드가 비싸져 코스트가 전반적으로 올라갑니다.

⚠️ `multiHit`은 크기 표에 **없다.** `damage`가 총량(damage × multiHit)으로
값을 내므로 multiHit까지 크기로 매기면 이중 청구가 된다. multiHit의
기본비용은 "여러 번 쪼개 때리는 유틸리티" 값으로만 남긴다.

`listActiveEffects`가 `cost`를 크기 반영값으로 덮어쓰고 `baseCost`를 따로
남긴다. 진단할 때 "기본 1점인데 크기 때문에 2.8점"인지 구분해야 어디서
예산이 샜는지 읽을 수 있다.

### 🐛 크기를 넣으면 **깎는 단계가 반드시 필요하다** (2-c)

크기가 예산에 들어가면 큰 수치 카드가 예산을 넘는다. 그때 기존 흐름은
**효과를 통째로 삭제**했다. "28 피해" 카드가 피해 효과를 잃는 것보다
"20 피해"로 줄어드는 편이 훨씬 낫다.

우선순위 (덜 파괴적인 것부터):

| 단계 | 무엇을 |
|---|---|
| 2 | 마나 코스트를 **올린다** |
| 2-a | 값을 치를 게 없으면 코스트를 **내린다** ([#69](#69)) |
| 2-b | 대상 범위를 좁힌다 (전체→3체→2체→단일) |
| **2-c** | **효과 크기를 깎는다** (등급 하한까지만) |
| 3 | 비싼 효과부터 제거 |
| 4 | 스탯을 깎는다 |

크기는 `RARITY_BALANCE_CAPS` 하한까지만 깎는다. 그 아래로 내려가면
등급 표기와 실제 성능이 어긋난다.

**검증.** 레전더리 6효과 카드(피해28+방어막26+회복26+드로우3+마나3+화상12×3):
효과 **하나도 삭제되지 않고** 16단계 크기 하향으로 예산에 들어갔다
(피해 20 / 방어막 18 / 회복 18 / 드로우 1 / 마나 1 / 화상 12×2턴).

### 🐛 깎았으면 설명문을 다시 맞춰야 한다

숫자 동기화(sanitize 3-E단계)는 예산 적용 **전**에 끝난다. 그래서 크기를
깎으면 카드에 "28 피해"라고 적혀 있는데 20이 들어갔다.
`trimmedValues > 0`이면 `syncDescriptionNumbers`를 한 번 더 돌린다.
건축물은 문장 전체가 데이터에서 생성되므로 `describeStructurePassive`로 재생성.

그 과정에서 `syncDescriptionNumbers`에 **드로우·마나 수급 규칙이 없던 것**을
발견했다. `drawCards`가 3→1로 깎여도 설명문은 "카드 3장을 뽑는다"로 남았다.
두 어순(`카드 3장` / `3장`)을 모두 잡도록 추가했다.

### ⚠️ enforcePowerBudget은 깊은 복사를 한다

2-c가 `statusEffect.value` / `passiveEffect.aura.attackBonus` 같은
**중첩 필드**를 깎는다. 얕은 복사(`{...skill}`)면 호출자의 원본까지 바뀌어
LLM 응답 객체가 조용히 변형된다. 중첩 객체는 따로 복사한다.

### 밸런스 영향 (부풀지 않았다)

전형적인 카드(중간 수치 + 효과 1~2개)가 안착하는 마나:

| 등급 | 소환수 | 마법 | 함정 | 건축물 |
|---|---|---|---|---|
| common | 2 | 2 | 1 | 2 |
| rare | 3 | 2 | 2 | 2 |
| epic | 3 | 3 | 3 | 3 |
| legendary | 4 | 3 | 3 | 3 |

전부 등급별 `costRange` 안이고 예산 소진율 48~100%다.
보관함 22장 중 예산 초과 0건.

## 71. 스탯은 **체증/체감 곡선**으로 값을 매긴다

**날짜:** 2026-09-01
**파일:** `js/config.js`

효과 크기는 [#70](#70)에서 값을 매겼지만 스탯은 여전히 선형이었다
(`공격력 / 5`). 그러면 공격력 26이 6의 정확히 4.3배 값이 된다.

실제 가치는 선형이 아니다:
- **공격력은 체증한다.** 고타점은 **한 방에 상대 소환수를 정리하는 문턱**을
  넘는다. 공격력 10짜리 두 기와 20짜리 한 기는 총합이 같아도 20짜리가 훨씬
  강하다 (교환에서 이기고, 도발을 뚫고, 처형 사거리가 길다).
- **체력은 체감한다.** 체력 40은 20의 두 배지만, 한 턴에 여러 번 맞으면
  죽고 방어막·회복으로 메울 수 있어 두 배만큼 강하지 않다.

```
STAT_CURVE = { attack: {exp:1.35, pivot:14}, hp: {exp:0.85, pivot:24}, defense: {exp:1.15, pivot:7} }
값 = (스탯/pivot)^exp × (pivot/단가)
```

⚠️ **기준점(pivot) 정규화가 핵심이다.** pivot에서는 선형과 정확히 같은 값이
나오도록 맞췄다. 그래서 전형적인 카드의 코스트는 그대로고 극단값만 벌어진다.
pivot을 옮기면 **모든 카드의 코스트가 움직인다.**

| 공격력 | 곡선 | 선형 |
|---|---|---|
| 6 | 0.89 | 1.20 |
| **14 (pivot)** | **2.80** | **2.80** |
| 26 | **6.46** | 5.20 |

| 체력 | 곡선 | 선형 |
|---|---|---|
| **24 (pivot)** | **2.40** | **2.40** |
| 40 | **3.70** | 4.00 |

**밸런스 영향.** 중간 스탯 카드는 코스트 그대로, 최대 스탯 카드만 한 마나씩 올라간다:

| 등급 | 중간 스탯 | 최대 스탯 |
|---|---|---|
| common | 2마나 | **3마나** |
| rare | 3마나 | **4마나** |
| legendary | 4마나 | **5마나** |

## 72. 행동 봉쇄·지속 피해 상태이상은 **소환수 전용**이다

**날짜:** 2026-09-01
**파일:** `js/status-effects.js`, `js/battle-engine.js`, `js/combat-side.js`,
`js/config.js`, `js/skill-effects.js`

### 🐛 기절은 절반만 구현되어 있었다

`consumeBlockingStatus`가 **보스 본체에게만** 호출됐다. 그래서:
- 소환수에 기절을 걸면 `entity.statuses`에 등록만 되고 **읽는 쪽이 없었다.**
  소환수 행동 판정은 `entity.frozen` 플래그만 봤고 그건 빙결 전용이었다
- 소환수의 화상·맹독은 **지속 피해를 틱하는 곳이 아예 없었다**
- 소환수 상태이상은 감쇠도 없어 한 번 걸리면 영구히 남았다

기본 카드 "프로스트 노바 & 기절"이 기절을 부여하는데 아무 일도 안 일어났다.

### 적용 범위 규칙

| 상태이상 | 본체 | 왜 |
|---|---|---|
| 기절 · 빙결 | ❌ | 한 턴을 통째로 빼앗는 건 게임이 아니라 벌칙이다 |
| 화상 · 맹독 | ❌ | 본체 체력이 낮아 방어막·회복으로 대응할 여지 없이 녹는다 |
| 감전 · 취약 | ✅ | **증폭기**라서 상대가 실제로 때려야 의미가 생긴다 |

`entityOnly: true`인 상태이상은 관문(`applyStatusRespectingScope`)이
**최전방 소환수로 돌리고**, 전장이 비어 있으면 불발시킨다.

⚠️ 이건 플레이어만 보호하는 게 아니라 **양방향**이다. 보스 콤보가
플레이어 본체를 맹독으로 녹이던 것도, 플레이어가 보스 본체를 태우던 것도
모두 보드 싸움으로 바뀐다.

### 본체를 노리고 싶으면 값을 치른다

`skill.bodyStatus = true`로 본체 지정을 **살 수 있다.**
`BODY_STATUS_COST_MULT = 2.5` — 화상 부여가 2점에서 **5점**으로 오른다.

⚠️ `config.js`의 `ENTITY_ONLY_STATUSES`는 `status-effects.js`의 `entityOnly`와
**반드시 같아야 한다.** config가 status-effects를 import하면 순환이 생겨
복제했다. 한쪽만 고치면 예산과 실제 동작이 어긋난다.

### 소환수 상태이상은 한 곳에서만 소모한다

`tickMinionStatuses(minions, label)` — 진영 턴 시작에 한 번:
1. 지속 피해 (화상·맹독) 적용, 죽으면 제거
2. 봉쇄 상태 1턴 소모 → `m.blockedBy` 설정
3. 봉쇄가 없으면 감쇠

⚠️ `combat-side.refreshMinions`는 **소모하지 않는다.** `m.blockedBy` 결과만
읽어 `canAttack`을 정한다. 두 곳에서 소모하면 기절이 절반 턴만 유지된다.
같은 이유로 `foeMinionAttack`도 플래그만 읽는다.

⚠️ 호출 순서: `tickMinionStatuses` → `refreshMinions`. 뒤집으면
`blockedBy`가 세워지기 전에 `canAttack = true`가 된다.

**검증.** 기절 1턴 → 1틱에 봉쇄, 2틱에 해제.
화상 6×3턴 → 60→54→48→42, 3틱 후 만료.
보스 맹독 → 플레이어 본체(50) 그대로, 아군 소환수에 화상 -8.
전장 빈 경우 → "화상은(는) 소환수 전용입니다 — 내 전장이 비어 불발."

### ❤️ maxHpGain — 본체 체력을 늘리는 카드

본체 체력이 낮은 게 근본 문제이므로 카드로 풀 수 있게 했다.
`maxHpGain` (cost 3, rare 이상, perUnit 5).

⚠️ **최대치만 올리지 않고 현재 체력도 같이 올린다.** 안 그러면
"최대 체력 +10"이 당장 아무 도움이 안 되고 회복 카드를 강요한다.

### ⚠️ 프롬프트 안에서 백틱을 쓰지 마세요

프롬프트는 템플릿 리터럴이다. 설명에 백틱을 넣으면 리터럴이 조기 종료돼
`SyntaxError: Unexpected identifier`가 난다. 큰따옴표를 쓰세요.

## 73. 소환수에게도 취약·감전이 동작한다 (그리고 로그가 근거를 보여준다)

**날짜:** 2026-09-01
**파일:** `js/skill-effects.js`, `js/battle-engine.js`, `js/status-effects.js`

### 🐛 취약·감전이 본체에만 구현돼 있었다

[#72](#72)에서 화상·맹독을 소환수 전용으로 옮기면서 지속 피해 틱을 만들었는데,
**취약(vulnerable)·감전(shock)은 여전히 소환수에서 무효과**였다.
두 효과는 `applyDirectDamageToPlayer`(본체 경로)에만 구현돼 있었고,
소환수 피해 계산(`damageEntity`)은 상태이상을 아예 보지 않았다.

`damageEntity`가 소환수 피해의 **단일 관문**(호출부 5곳 전부 경유)이라
여기 한 곳만 고치면 모든 경로가 덮인다.

### 적용 순서는 본체와 같아야 한다

```
수비력 흡수 → 💥 취약 배율 → ⚡ 감전 추가피해
```

⚠️ 순서가 다르면 **같은 상태이상이 대상에 따라 다른 피해**를 낸다.
본체 경로(`applyDirectDamageToPlayer`)는 경감 → 취약 → 감전이므로 맞췄다.

감전은 **수비력을 무시한다** (전기는 갑옷을 타고 흐른다). 실제로 맞았을 때만 터진다.

**검증** (피해 20, 수비력 3 기준):

| 상태 | 결과 |
|---|---|
| 없음 | 17 (방어 3 흡수) |
| 취약 | **25** (증폭 +8) |
| 감전 6 | **23** (감전 +6) |
| 취약 + 감전 | **31** |
| 관통 + 취약 | **30** (수비력 무시) |

### 🐛 로그가 요청한 피해를 찍고 있었다

`addBattleLog(...-${dmg} 피해!)` — **요청값**이지 실제 들어간 값이 아니었다.
수비력·취약·감전이 붙으면 로그가 거짓이 된다. 반환값(`hit.dealt`)을 쓰고,
`describeDamageExtras()`로 근거를 덧붙인다:

```
🗡️ [보스 부하] ➔ [취약병] 공격! (-31 HP) (방어 3 흡수, 💥 취약 +8, ⚡ 감전 +6)
```

수치가 왜 그렇게 나왔는지 보여주지 않으면 상태이상이 동작하는지 알 수 없다.

### 🐛 소환수 카드에 상태이상이 보이지 않았다

렌더링이 `entity.frozen`만 봤다. 그래서 **기절은 화면에 아무 표시도 없었고**
화상·맹독·감전·취약도 전부 안 보였다. 동작해도 플레이어가 모른다.

- 행동 봉쇄(기절·빙결) → 카드 전체를 덮는 오버레이 (`entity.blockedBy` 기준)
- 나머지 → 우측 상단 아이콘 띠에 남은 턴 표시

이를 위해 `describeStatuses()`가 `turns`/`value`도 반환한다.

## 74. 대상 진영(targetSide)이 효과 성격과 맞는지 검사한다

**날짜:** 2026-09-01
**파일:** `js/config.js`, `js/effect-targets.js`, `js/skill-effects.js`, `js/archetype-service.js`

### 증상: "자신 1체에 12 피해"

두 겹의 문제였다.

**(1) `targetSide`는 스킬 하나에 한 개뿐인데 효과마다 대상이 다르다.**
"적에게 12 피해 + 내 방어막 8" 같은 카드에서 LLM이 방어막을 보고 `self`를
고르면 **피해까지 자신을 향하게 된다.** 프롬프트가
"대상이 필요 없는 효과(내 방어막, 마나 수급)는 self로 둘 것"이라고
지시한 게 직접적인 유인이었다 — 그 문구를 고쳤다.

**(2) 그런데 이 엔진에는 자기 피해(sacrifice) 메커니즘이 없다.**
`self`는 `collectTargetKeys`에 분기가 없어 대상 키가 0개이고
`needsTargetPick`도 false다. 그래서 피해가 조용히 `dealDamageToBoss`로
흘러갔다 — **카드엔 "자신"이라 적히고 실제로는 보스를 때렸다.**

### 같은 부류를 전부 훑었다

| 조합 | 문제 | 교정 |
|---|---|---|
| `self` + 피해/디버프 | 대상이 없어 보스로 흘러감 | → `foe` |
| `ally` + 피해/디버프 | **더 나쁘다.** collectTargetKeys가 아군을 내주므로 "내 소환수를 골라 때리라"고 요구 | → `foe` |
| `foe` + 회복/방어막 | 엔진은 무조건 내 쪽에 적용 → 설명이 거짓 | → `ally` |
| 회복만 있는 카드 | 대상 선택을 **요구하고도 무시**했다 | heal이 picked를 존중 |

교정 시 설명문에 옛 대상이 남아 있으면 `describeSkillFromData()`로
문장 전체를 다시 만든다 (부분 치환은 조사가 어긋난다).

### `describeTarget('self')`은 "자신"이다

`self`는 **이 카드 자신**이라 셀 수 있는 대상이 아니다.
예전에는 `${s} 1체` 규칙이 그대로 적용돼 "자신 1체"가 나왔다.

### 🐛 heal이 고른 대상을 무시했다

`hasTargetableEffect`에 heal이 있어 `needsTargetPick`은 true인데,
heal 처리는 `readHpTarget`만 보고 `opts.picked`를 읽지 않았다.
플레이어가 아군을 골라도 본체가 회복됐다.

이제 picked에 아군 소환수가 있으면 **그 소환수들을** 회복한다.
덕분에 "아군 1체 체력 회복"이 실제 카드가 된다 (예전에는
`hpTarget: 'minion'`으로 "이 카드 자신"만 가능했다).

**검증.** 부상병A(20/60)를 지정 → 40으로 회복. 미지정 B와 본체는 그대로.

### rebalanceExistingCards가 대상 교정도 잡는다

⚠️ 대상 교정은 **코스트나 효과 수를 바꾸지 않아** 예전 감지 조건
(초과/마나/효과/스탯)에 걸리지 않았다. `targetSide`·`targetScope`·설명문
변경도 감지 조건에 넣었다. 사유 표시에 '대상 교정' / '설명문 교정'을 추가.

## 75. 초반 밸런스 — 보스 공세 램프 · 코스트 우선 생성 · 바닐라 카드

**날짜:** 2026-09-01
**파일:** `js/battle-engine.js`, `js/combat-side.js`, `js/config.js`,
`js/card-forge.js`, `js/card-pack.js`, `js/card-renderer.js`, `js/card-detail.js`

### 증상

"1코가 첫턴에 없으면 아무것도 못하고 바로 턴 넘기고 죽어버려."

측정(플레이어가 패스만 할 때): **턴1 보스 딜 59, 플레이어 체력 50 → 2턴 사망.**
첫 손패에 1코가 올 확률 **0%**.

⚠️ **시작 마나를 늘리는 것으로는 안 풀린다.** 3마나로 시작해도 낸 소환수는
소환 후유증으로 방어만 가능하고, 보스 딜은 그대로다. 실제로 측정해서 확인했다.

### 원인 ① 보스 소환수에 소환 후유증이 없었다

공격 루프(`bossMinions.forEach(foeMinionAttack)`)에 `canAttack` 검사가 **아예 없었고**,
소환 지점도 후유증을 붙이지 않았다. 스텝1에 소환된 소환수가 같은 턴 스텝4에 때렸다.
플레이어 소환수는 후유증이 있으므로 **한쪽만 불리한 비대칭**이었다.

`summonedTurn`(소환된 턴 번호)을 기록하고 `refreshMinions`가
`summonedTurn >= state.turnCount`인 것은 풀어주지 않는다.

⚠️ `refreshMinions`를 콤보 실행 **앞에** 불러야 한다. 뒤에 두면 이번 턴에
소환된 소환수까지 풀려 후유증이 무효가 된다.

### 원인 ② 보스가 소환수 2기를 깔고 시작했다

플레이어는 1마나뿐인 1턴에 막을 것을 낼 수 없는데 그 2기가 곧바로 본체를 때렸다.
**전장을 비워서 시작한다.** 보스는 콤보로 매 턴 소환하므로
압박을 없애는 게 아니라 **뒤로 미루는 것**이다.

### 원인 ③ 보스가 마나 제약 없이 1턴부터 전력을 쏟았다

`foeVirtualMana: 99`라 턴1에 소환수 3기 + 카드 2~3장을 냈다.
`BOSS_RAMP`로 턴1~2를 소환수 1~2기 / 카드 1장으로 제한한다. 3턴부터는 그대로다.

**턴1 딜 59 → 34 → 16~24.**

### 원인 ④ (가장 큰 것) 등급이 코스트를 가뒀다

`costRange`가 등급별로 좁았다 — 커먼 1~2, 레어 2~3, 에픽 3~4, 레전더리 3~5.
**레어 이상은 1마나가 될 수 없었다.** 측정한 활성 덱 13장 커브가
`2코1·3코6·4코1·5코2·6코3` — 1코 0장.

**코스트를 먼저 정한다.** `COST_CURVE_WEIGHTS`(덱 커브를 닮은 분포)에서 굴려
LLM에 넘기고, 등급은 "그 코스트에서 얼마나 강한가"(파워 밀도)만 정한다.
1마나 레전더리는 "효율 좋은 작은 카드"로 성립한다.

`costLocked: true`를 붙여 예산이 코스트를 움직이는 대신 **내용을 깎게** 한다.
⚠️ 이게 없으면 등급별 스탯 하한(레전더리 공18/체30) 때문에 1마나 카드가
전부 2마나로 밀려 올라간다 (측정: 잠금 전 최종 커브 2코 64% / 1코 0%).

| | 전 | 후 |
|---|---|---|
| 최종 커브 | 2코1·3코6·4코1·5코2·6코3 | 1코 20% · 2코 25% · 3코 22% · 4코 17% · 5코 15% |
| 첫패 1코 확률 | **0%** | **60%** |
| 첫패 2코 이하 | 30% | **91%** |

### 🐛 그 과정에서 찾은 것 — 생성 카드의 25%가 예산 초과였다

"효과가 전부 사라졌으면 기본 피해 하나는 남긴다" 폴백이 **맨 마지막**에 있었다.
3단계가 예산을 맞추려고 지운 효과를 여기서 되살려, 검사를 통과한 **뒤에**
카드가 조용히 예산을 넘겼다. 스탯 깎기 앞으로 옮겨 정산에 포함시켰다. → 0%.

### 🃏 바닐라 카드

위 폴백은 애초에 **"모든 카드가 효과를 가져야 한다"는 틀린 전제**였다.
저코스트 카드는 스탯만으로 예산이 차서 효과를 넣을 자리가 없다.
실제 TCG에서 그건 정상적인 카드 종류다 — 바닐라.

효과가 하나도 안 남으면 `skill.isVanilla = true`가 되고, 설명 슬롯에
**플레이버 텍스트**가 들어간다 (LLM의 `flavorText` → 없으면 `defaultFlavorText`).

⚠️ 기본 플레이버는 `Math.random()`이 아니라 **이름 해시**로 고른다.
카드 상세를 다시 열 때마다 문구가 바뀌면 버그처럼 보인다.

⚠️ 예산에 밀려 바닐라가 된 경우, 남아 있던 효과 설명문은 **전부 거짓**이므로
반드시 갈아치운다 ("적 1체에게 12의 피해" → 플레이버).

렌더링은 기울임 + 흐린 색으로 효과 설명과 구분한다. 카드 상세에는
"🃏 바닐라 — 효과 없이 스탯으로 싸운다"를 붙여 실패작으로 오해받지 않게 한다.

### 남은 것

예산이 넘칠 때 **효과 제거(3단계)가 스탯 깎기(4단계)보다 먼저**다. 그래서
스탯 상한 근처의 카드는 효과를 통째로 잃고 바닐라가 된다 (합성 최악 조건에서 23%).
효과가 카드의 정체성이라면 순서를 뒤집는 게 맞지만, 그건 모든 카드의 스탯을
낮추는 큰 변화라 이번엔 하지 않았다.

## 76. 설명문 **2단계 생성** · 스탯 깎기 우선 · 바닐라는 소환수 전용

**날짜:** 2026-09-01
**파일:** `js/card-describe.js`(신규), `js/config.js`, `js/card-forge.js`, `js/card-pack.js`

### ✍️ 설명문을 두 번째 호출로 분리했다

한 번의 호출로 수치와 설명문을 같이 받으면 둘이 어긋난다. 지금까지 그걸
`syncDescriptionNumbers` / `describeSkillFromData`로 **뒤에서 고쳐** 왔다.

이제 나눈다:
1. **1단계** — LLM이 이름·수치·효과를 정한다 (설명문은 신경 쓰지 않는다)
2. **엔진** — 예산으로 수치를 확정한다 (깎기·제거·코스트 조정)
3. **2단계** — 확정된 수치를 보여주고 **그에 맞는 문장만** 쓰게 한다

⚠️ **그래도 LLM을 믿지 않는다.** 2단계 출력도 검증하고 어긋나면
`describeSkillFromData`(결정론적)로 되돌린다. 실측 채택률 **67~80%**,
나머지는 폴백 — 즉 **거짓 설명이 나갈 확률은 0**이다.

검증 기준은 스킬 필드가 아니라 **확정 문장(facts)**이다:
- facts에 없는 효과를 언급하면 반려
- facts의 숫자를 하나라도 빠뜨리면 반려

🐛 필드로 대조했더니 오탐이 났다 — 건축물 방어막은 `skill.shield`가 아니라
`passiveEffect.endTurnShield`에서 온다. facts 기준이면 패시브·오라·새 효과까지
자동으로 커버된다.

**구현하며 걸린 함정 둘:**
- `callOllamaChat`은 응답을 **JSON으로 파싱**한다. 평문을 요구하면 통째로
  실패한다 (처음엔 100% 폴백이었다). `{"description": "..."}`로 받는다.
- 카드 정보를 **system에만** 넣으면 4B 모델이 무시하고
  "이 카드의 설명은 제공되지 않았습니다"를 돌려준다. **user 메시지에** 넣는다.

### 📉 스탯 깎기를 효과 제거보다 **먼저**

효과는 카드의 **정체성**이고 스탯은 상대적으로 대체 가능하다.
"12 피해를 주는 8/18"이 "아무것도 안 하는 10/22"보다 카드답다.

단계: 코스트 조정 → 대상 축소 → 크기 깎기 → **스탯 깎기(등급 하한까지)**
→ 효과 제거 → 스탯 깎기(절대 하한) → 코스트 안전밸브

⚠️ 3단계는 **등급 하한까지만** 깎는다. 그 아래로 내려가면 등급 표기와 실제
성능이 어긋난다 — 그건 5단계의 일이다.

| 코스트 | 바닐라 비율 (전 → 후) |
|---|---|
| 1코 | 100% (최소 스탯만으로 예산이 참 — 불가피) |
| 2코 | 13% |
| **3코 이상** | 23% → **0%** (효과가 전부 보존됨) |

### 🃏 바닐라는 **소환수 전용**

소환수는 효과가 없어도 스탯으로 싸우지만, 마법·함정·건축물은 효과가 **전부**다.
효과를 다 지우면 발동해도 아무 일이 없는 백지 카드가 된다.
(실측: 효과 없는 함정 "운명을 뒤집는 계략"이 실제로 생성됐다)

효과 제거 루프가 `cardType !== 'unit'`이면 **마지막 효과를 남긴다.**
그래도 비면 최소 효과를 주입한다 (건축물은 패시브, 나머지는 최소 피해).

### 🐛 60장 뽑아보고 찾은 것들

| 증상 | 원인 |
|---|---|
| 60장 중 55장 **설명문 없음** | `if (skill.description)`일 때만 문장을 손봤다. 2단계 설계에서는 1단계가 설명문을 안 쓰는 게 정상이라 치명적이 됐다 |

전부 패시브를 정상 서술. 2단계 LLM 실호출 채택률 8/10.

## 77. 실팩 검증에서 드러난 것 — 함정은 전부 死카드였다

**날짜:** 2026-09-01
**파일:** `js/config.js`, `js/card-pack.js`, `js/card-describe.js`, `js/archetype-service.js`

Ollama를 켜고 **실제 LLM 경로로 14팩(70장)**을 열어 검증했다.
합성 입력으로는 안 보이던 것들이 나왔다.

### 🪤 생성된 함정이 **전부** 발동조건 없이 나왔다 (6/6)

카드팩 프롬프트는 `trapTrigger`를 요구하는데, **응답에서 읽지를 않았다.**
스킬 조립부에 `trapTrigger` 필드가 아예 없어서 LLM이 줘도 버려졌다.
발동조건 없는 함정은 영영 발동하지 않는다 — 필드에 놓이고 아무 일도 없다.

세 겹으로 막았다:
1. 카드팩이 `cardJson.trapTrigger` / `condition`을 읽어 스킬에 싣는다
2. sanitize가 함정에 조건이 없거나 알 수 없는 값이면 `normalizeTrapTrigger`로 채운다
   (`trap-system.js`가 단일 소스 — config에 목록을 복제하지 않는다)
3. `rebalanceExistingCards`가 조건 보정도 감지한다 (전에는 코스트·효과·스탯만 봤다)

### 🪤 `trapTrigger`를 효과로 세고 있었다

`listActiveEffects`가 trapTrigger를 포함하므로, **효과가 0인 함정이
"효과 1개"로 통과**했다. 설명문이 "조건 충족 시 발동합니다."만 남고
터져도 아무 일이 없었다.

⚠️ **trapTrigger는 조건이지 효과가 아니다.** 효과 수를 셀 때 빼야 한다.
(비소환수 최소 효과 보장 · 마지막 효과 유지 두 곳 모두)

또 카드팩이 함정의 damage를 `atk`으로 잡고 있었다 — 함정은 공격력이 0이라
피해도 0이 됐다. 주문과 같이 `spellDmg`를 쓴다.

### ✍️ 2단계 실패 시 **1단계 원문을 남기면 안 된다**

처음에는 "실패하면 기존 설명문을 그대로 둔다 — sanitize가 맞춰뒀으니 정확하다"고
했다. 틀렸다. sanitize는 원문이 **있으면** 숫자만 맞출 뿐 통째로 다시 쓰지 않는다.
그래서 구현되지 않은 서술이 살아남았다:

| 실팩에서 나온 문장 | 왜 거짓인가 |
|---|---|
| "적의 공격 피해 **160%** 감소" | damageReduction은 5~40으로 클램프된다 |
| "[성역의 수호사제] 카드에 12의 방어막" | 특정 카드 지정은 구현되지 않았다 |
| "[성역] 카드가 필드에 있을 때:" | 조건부 발동은 함정 전용이다 |

이제 2단계가 실패하면 **결정론적 문장으로 교체**한다.
플레이버를 잃더라도 정확한 문장이 이긴다.

### 🪤 함정 설명문에 발동 조건을 붙인다

"적 1체에게 12 피해"만 적으면 플레이어가 언제 터지는지 몰라 세트할 판단을 못 한다.
→ "상대가 소환수를 낼 때: 적 1체에게 12 피해."

### 실측 결과

| 항목 | 결과 |
|---|---|
| 실팩 24장 (LLM 1·2단계) | 예산 초과 0 · 설명 누락 0 · 비소환수 바닐라 0 · 숫자 불일치 0 |
| 코스트 커브 | 1코 6 · 2코 3 · 3코 7 · 4코 2 · 5코 6 (1코가 실제로 나온다) |
| 2단계 채택률 | 약 40~80% (나머지는 결정론적 문장으로 폴백) |
| 팩당 소요 | 약 25~45초 (카드당 LLM 2회) |

⚠️ 2단계 반려 사유는 대부분 **모델이 없는 효과(방어막·마나)를 지어낸 것**이다.
검증기가 그걸 잡아내므로 거짓 설명이 나갈 확률은 0이다.

## 78. 프롬프트를 **카드 타입별로 잘라** 보낸다

**날짜:** 2026-09-01
**파일:** `js/card-type-rules.js`(신규), `js/card-pack.js`, `js/card-forge.js`, `js/card-describe.js`

### 카드 타입은 이미 미리 정하고 있었다

카드팩은 생성 **전에** 타입을 굴려(`unit 55% / spell 22% / structure 13% / trap 10%`)
프롬프트에 `Type: "${cardType}"`으로 넘긴다. 그건 문제가 아니었다.

**문제는 프롬프트가 네 타입 규칙을 전부 실었다는 것이다.**
소환수를 만들 때도 함정 발동조건·건축물 패시브·바닐라 규칙이 같이 들어갔다.
그러면 LLM이 타입 특징을 섞는다 — 실제로 이런 것들이 나왔다:
- 소환수에 "상대가 소환수를 낼 때" 같은 **함정식 반응 효과**
- 함정에 "0 공격을 가합니다" 같은 **소환수 문구**
- 건축물에 **인물 이름**

관계없는 규칙은 노이즈일 뿐 아니라 **섞임의 원인**이다.

### card-type-rules.js — 타입 규칙 한 곳

`cardTypeRules(cardType)`이 그 타입 것만 돌려준다. 두 부분으로 짠다:

1. **정체성** — "이 카드는 무엇인가"를 한 줄로 못박고, **다른 타입 전용 기능을
   명시적으로 금지**한다. ("❌ 반응형 효과는 쓸 수 없다 — 함정 전용이다")
2. **고유 규칙** — 그 타입만의 상세 (바닐라 / 패시브 / 발동조건 …)

프롬프트 길이가 크게 줄었다 (소환수 기준 약 2400자 → 458자).
`cardTypeStatRule(cardType)`은 스키마 옆에 붙는 스탯 지침으로,
마법·함정은 `"attack": 0` 을 못박는다.

⚠️ 규칙을 고칠 때는 **이 파일 한 곳**만 본다. card-forge와 card-pack이 공유한다.

**검증.** 실팩 8팩(24장) — 타입 섞임 **0건**, 예산 초과 0, 설명 누락 0,
함정 트리거 누락 0, 마법·함정 스탯 0, 건축물 공격력 0.
코스트 커브 1코 9 · 2코 4 · 3코 4 · 4코 4 · 5코 3.

### 🐛 2단계 검증기가 **엔진에 없는 동작**을 놓치고 있었다

실팩에서 이게 통과했다:

> "적 1체에게 9의 번개 피해를 입히며 **사령관을 소환한다**"

소환은 스킬 효과가 아니다. 검증기의 `CLAIM_PATTERNS`는 구현된 효과 키워드만
갖고 있어서, **아예 없는 동작**은 검사 대상이 아니었다.

TCG 관용구로 LLM이 자주 지어내는 것들을 추가했다:
`소환 · 부활 · 파괴 · 제거 · 훔침 · 변신`.
이들은 `facts`에 나올 수 없으므로 언급되면 무조건 반려된다.

⚠️ **한국어 활용형에 주의.** `/훔치/`만 두면 "훔**친**다"를 놓친다.
어간이 바뀌는 동사는 활용형도 함께 넣어야 한다 (실제로 놓쳤다).
